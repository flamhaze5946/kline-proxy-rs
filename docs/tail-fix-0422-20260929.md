# Rust 0.4.22 长尾修复与实例验证

2026-09-29，时间均为 UTC。已完成本轮确认的代码和 Nginx 修复，并部署到 `market-mirror.feng.dog`。Java `market.feng.dog` 保持 1.8.3，作为在线对照。

常用缓存接口未再出现秒级等待；原有元数据调度饥饿已有复现、回归测试和线上刷新证据。200×5 bulk 的中位耗时下降，p99 基本持平。真正的首次 REST 加载、交易所硬配额、网络和 VPS 抢占仍可能增加延迟，不能把有限样本解释为任何条件下都没有长尾。

| 已修复问题 | 原因 | 0.4.22 行为与验证 |
|---|---|---|
| 元数据排队数十秒 | 连续启动/重连恢复使用 Urgent；较小权重请求持续拿走额度，较大的 exchangeInfo 无法获得完整额度 | 独立保留元数据和价格刷新额度；Urgent 短突发用完后降到普通前台优先级；硬分钟预算、429/418 冷却保留 |
| 刷新拖住元数据查询 | 清除缓存后等待网络重新加载 | 元数据、编码字节和币种索引原子发布；提前刷新，有效快照直接返回；原硬过期门槛保持 |
| 辅助 CPU 工作干扰行情 | 大 JSON、归档、统计计算共享执行资源 | 大任务先取得独立许可，最多占用一个 market worker；Yama 三类结果共用一次计算，使用独立统计 worker |
| 大 bulk 排满小查询入口 | 大任务能占满全部 64 个通用槽位 | 大任务最多取得 8 个入队许可，给近期小查询保留入口；覆盖 128 个大任务排队及取消测试 |
| 多币价格已有内存值仍等待 REST | 缺少排序排名时强制等待基线；把刷新节奏当作基线有效期 | 既有排名保持，新币追加；缺排名只触发后台刷新；多币价格基线有效期与全市场的 10 秒硬上限一致 |
| 资金费率组合重复回源 | 不同 symbol 组合各自加载相同币种 | 近期查询按 symbol、limit、小时、修订号共享 60 秒缓存；不叠加第二个缓存有效期；原始代理及范围查询保留语义 |
| Nginx 连接资源和复用 | upstream 空闲池 64、15 秒超时不足以覆盖整点间隔 | 每 worker 256 个 upstream 空闲连接、65 分钟空闲期限、2 小时连接寿命；worker_connections 2048；TLS session cache 10 MiB/1 天 |

新增调度回归用 8 个持续 Urgent 回补任务，同时发送价格和元数据请求，共 120 轮。把同一测试放回 0.4.21 调度器，第 31 次价格请求排队 15 秒而失败；最终调度器通过，测试中的价格/元数据等待不超过 2 秒，并检查总权重未越过 1200/min。它验证指定负载下的公平性，不是任意流量或上游冷却下的绝对 SLA。

元数据 exchangeInfo/普通校验仍采用 300 秒硬期限，ticker 币种查询保留原有 600 秒宽限；刷新约提前到 240 秒，失败保留旧快照但不修改其年龄。多币价格现在沿用全市场已有的 10 秒 REST 基线硬期限，优先新鲜 WS，合约 v2 使用真实来源时间戳；重新编码不会重置数据年龄。单币价格和 K 线 REST 策略未更改。

近期 K 线查询仍不触发即时 REST 回补；初始化、实际重连、新目录加载和定时订正按原策略运行。当前零成交量 bar 仍要求紧邻上一根的真实 WS `x=true`，没有用 REST 推断此条件。

普通查询每接口、每服务 500 次，共 5000 次/服务；另做 10 轮 200 客户端 × 每客户端 5 个分散 symbol 的合约 bulk，共 2000 次/服务。最近 10 根、closed_only、732 个共同可用 symbol，前后使用同一压测程序 SHA；TLS 校验开启、连接复用、主机顺序交替、计时至完整响应体，失败和最慢样本全部保留。

CPU 按两台服务共同时间窗口的累计 CPU 计数计算，前后窗口分别约 97 秒和 100 秒。宿主机抢占和后台流量不同，Java 同期 CPU 也有变化；RSS 受重启后运行时长影响。因此不能把全部差值归因于此次修改，也不能宣称 Rust 的 CPU 已全面低于 Java。

最慢 Rust bulk 请求 `kp0419-0.4.22-rust-future-reuse-04-009`：客户端 36.78 ms，Nginx request/upstream response 31 ms，upstream connect 8 ms；同波次附近一秒采样 steal 约 12%～17%。应用累计 3062 次构建：编码 p99 上界 0.1 ms、最大 2.58 ms，构建排队 p99 上界 10 ms、最大 9.14 ms。两组数据的统计范围不同，不能将各自 p99 相加或把每个请求都精确分摊，但支持剩余尾延迟包含调度与本机接入成本。

最终构建保留符号；60 秒独立 perf 采样没有丢样。采样 CPU 约 33% 在内核，用户态可见 WS 解码/调度、分配/释放和行情快照编码。行情编码函数自身约 2.9% 的采样，不是整颗 CPU 的占用比例；在这段行情请求采样中，统计和 bulk worker 未占据主导。原始 perf 数据保留在 Rust VPS 的 `/var/tmp/kp-tail-fix-0419-20260929/profile/after-symbolized.data`，本地保存符号报告和资源采样。
