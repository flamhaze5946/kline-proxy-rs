**Java 1.8.1 与 Rust 0.4.4：东京实例性能对照**

2026-09-17，独立东京测试机 `192.0.2.10` 请求 Java `market.feng.dog`（192.0.2.30）与 Rust `market-mirror.feng.dog`（192.0.2.40）。两台服务实例均为 Skylake 2 vCPU、约 4 GiB 内存。本轮没有更换程序、配置或重启服务。

实测结论：Rust 的单币行情、最近 10 根 K 线与合约 bulk 更快，当前驻留内存低约 62.5%；但应用 CPU 更高，全市场价格列表也慢于 Java。不能据此宣称全面胜出或将全部差距归因于语言。

**全市场价格列表仍需优化**

独立窗口 08:42:18.110–08:42:48.162 UTC，预热后每版每市场 40 次。样本较少，下表报告最大值而非把它包装成稳定生产 p99。

| 全市场价格 | Java p50 | Rust p50 | Java 最大 | Rust 最大 |
|---|---:|---:|---:|---:|
| 合约 | 3.11ms | 4.44ms | 5.78ms | 11.81ms |
| 现货 | 5.24ms | 8.62ms | 9.67ms | 559.14ms |

现货慢样本为第 13 次，08:42:27.877 发起，08:42:28.436 完成。同期后台现货全价回填 `rest_id=22530` 的本地额度等待为 3596.69ms，Binance HTTP 为 9.10ms，首次尝试成功且无冷却。结合 3 秒快照新鲜度检查及共享加载实现，这符合前台等待正在进行的回填的行为；没有前台与该后台加载的独立关联 ID，不能把这笔前台 559ms 逐毫秒归因。全市场列表目前仍需要 REST 维持完整覆盖，不能将单币 WS 收益直接推广至该路径。

09:09–09:15 UTC 补充核对线上 Java JAR 与 Rust 读取路径，确认两处差异：

- Java 全价快照非空时，直接返回该快照，过期刷新在后台异步执行；控制器在快照对象未变时复用已编码的 JSON。Rust 全价响应缓存仅 100ms，未命中时在请求内逐币合并 WS 值、复制 JSON 值并重新编码完整列表。这是明确的额外工作，但没有分段 CPU 剖析，不能把常态 1–3ms 差额全部归到编码。
- Rust REST 快照超过 3 秒后，只有完整列表的每一行都具有新鲜 WS 值才能直接使用；否则会等待 `refresh_prices`，包括等待已在刷新的后台任务及本地限流器。Java 有快照时没有这个前台等待分支，因此两者延迟和新鲜度策略不同。

09:15:32 UTC 在 Rust 实例回环接口核对现货列表与交易元数据：全价 3708 行，其中 `TRADING` 1372 行、`BREAK` 2333 行、元数据缺失 3 行。现货 WS 只订阅 `TRADING`，但 `Live::complete` 对 3708 行全部要求 3 秒内的新鲜 WS 值；2336 行不具备订阅资格，完整覆盖条件无法长期成立。这是当前集合定义的实现问题；这次计数不是 08:42 历史 WS 覆盖率的回溯测量。即便只计交易中币对，事件流暂时没有新事件也不能直接等同于连接失效或价格错误。

优化方向是后台合并并发布预编码的不可变快照，让请求直接读取；明确区分交易中币对、非交易币对及未知币对，分别管理更新与 REST 校验；以连接健康、事件语义和明确的数据年龄预算决定回退，避免一个缺少 WS 更新的币对让整个列表等待。须保留返回集合和时间语义，不能单纯无限放宽过期时间换取低延迟。

**已核实的 Java 额度问题与结论边界**

09:09:43 UTC 从当前运行 JAR 提取父类与子类字节码，进一步确认：带单个 `symbol` 的价格和 24h ticker 都先调用 `queryTickersBySymbols` / `queryTicker24HrsBySymbols`，由子类先获取本地 REST 额度再访问 Binance；该调用返回非空时直接返回。只有结果为空才继续到内存回退，不能描述为“内存缺失才请求 REST”，也不能描述为“所有 REST 异常都自动回退”。K 线的缺口补齐与全市场 ticker 的快照读取是另外的调用路径。完整字节码留存在 `java-query-paths.json`，JAR SHA-256 与下面实例指纹一致。

从正在运行的 Java JAR 提取字节码，确认合约与现货单币 `queryTicker24HrsBySymbols` 都会先调用本地 limiter，权重分别为 40、80；这是全市场请求的权重。官方单币权重分别为 1、2，因此本地额度计数放大了 40 倍。此事实与秒级等待一致，但本轮未给 Java 添加逐请求排队/HTTP 分段计时，不据此声称每笔慢请求都已完全定因。[Binance 合约文档](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/market-data#24hr-ticker-price-change-statistics)，[Binance 现货文档](https://developers.binance.com/en/docs/catalog/core-trading-spot-trading/api/rest-api/market#24hr-ticker-price-change-statistics)。

建议优先让 Rust 承担已验证的近期 K 线、合约 bulk 与单币行情读取；在全面替换前，继续优化全市场价格回填和后台/全市场成交订阅的 CPU 成本。Java 单币 ticker 的本地权重也值得单独修正，不能把该实现问题算成 Rust 语言本身的速度优势。本轮是非整点短测，未重演生产整点 Lambda 洪峰，也未测完整功能集的最大容量。
