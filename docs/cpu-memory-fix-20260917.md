**Rust 0.4.6 CPU、内存与延迟修复报告 — 2026-09-17**

0.4.6 已于 11:36:02 UTC 部署到 `market-mirror.feng.dog`（192.0.2.40）。本轮修复普通 K 线全量复制、行情消息重复解析及对象复制、小消息逐条跨线程交接、全市场价格重复编码四类开销。配置、数据保留数量、订阅范围和新鲜度规则保持原有语义。

实测 CPU 下降约 **35%**，线程切换下降约 **71%**，RSS 观察值下降约 **17%**。全市场价格与普通 K 线的部分尾延迟改善；**尚不能认定所有延迟指标都改善，也没有证明 Rust CPU 已低于 Java**。

**实例 CPU 与内存**

Rust 修复前窗口为 11:22:26–11:23:36 UTC，修复后为 11:43:55–11:45:05 UTC；Java 为 11:43:57–11:45:07 UTC。修复后成交消息输入 578 条/秒，修复前 536 条/秒；现货 ticker 为 276 对 245 条/秒。两个市场价格发布仍约 10 次/秒。CPU 收益并非来自缩减这些订阅或降低快照频率。

这不是完全相同输入的重放：REST 刷新次数与市场流量不同，Java 还承接自身业务流量，机器性能和订阅实现也不完全相同。新 Rust 进程 uptime 较短；两次资金费率缓存分别有 336/332 个小时，已完成归档加载，K 线均已全部就绪。因此 RSS 降幅是完整加载后的观察结果，不能全部归因于代码改动或当作长期内存上限。

`smaps` 进一步显示：主 heap 驻留约 446.71→446.09 MiB，匿名映射约 391.59→248.66 MiB，文件映射约 13.39→12.90 MiB；两次均无 swap。RSS 变化主要位于匿名映射，单凭这些映射不能继续断言具体业务对象的占比。对象级分配证据由下述隔离实验提供。[CPU 原始汇总](../research/results/cpu-memory-fix-20260917/summary.json)、[修复前 smaps](../research/results/cpu-memory-fix-20260917/before-smaps.json)、[修复后 smaps](../research/results/cpu-memory-fix-20260917/after-smaps.json)。

**改动与分配证据**

- 普通 K 线：在有序环形历史中二分定位时间范围，只复制命中的记录，保留内部缺口、首尾边界及默认时间窗口回退。业务查询逻辑留在 market 层，core 提供范围读取，service 提供一致的读锁视图。
- 行情消息：借用 JSON 字段，普通十进制字符串直接保留精度及小数位；特殊数字继续走旧格式化路径。完整 ticker 由两个缓存共享不可变对象，成交价使用小型结构保存。
- 小消息调度：4096 字节以内的帧就地处理，每 32 帧主动让出执行权；大数组继续由有界辅助线程池处理，减少每条消息的线程唤醒和队列往返。
- 全市场价格：价格行在更新时编码一次，快照拼接已经编码的有效行；完整 REST 列表仍定义币种覆盖及顺序，成交时间水位、断线失效和过期限制保持原有规则。

东京专用测试机使用同一个 `bench.rs` 对照修复前后的库；外部依赖版本及校验和一致，编译配置一致。原生耗时取交替执行五轮的中位数，heaptrack 单独执行，用于统计分配；没有用带 heaptrack 开销的耗时计算加速比。K 线每轮 3 万次查询，行情每轮 2 万条消息，行情时间和序号持续更新，并断言所有输入实际处理。

**CPU 调用栈与剩余开销**

修复后另采集 60 秒 perf，199Hz，1463 个样本，无丢失样本和符号解析警告。采样直接使用运行中 0.4.6 二进制的符号；该窗口不混入上述延迟或无 profiler 的 CPU 结果。与上一轮 0.4.5 活跃场景的采样作方向性对照：

| 栈中出现的类别 | 0.4.5 样本占比 | 0.4.6 样本占比 |
|---|---:|---:|
| futex 等待/唤醒路径 | 15.60% | 3.35% |
| 辅助线程消息队列 | 6.13% | 0.55% |
| malloc/free/realloc | 16.13% | 10.53% |
| 全市场价格编码/拼接路径 | 17.42% | 10.18% |
| ticker/成交消息处理路径 | 16.29% | 15.24% |
| 后台 reconcile 校验路径 | 6.78% | 12.17% |

这是含子调用的栈出现比例，类别重叠，不能相加；两个市场时段的输入也不同。整体 CPU 已下降，某项占比提高不等于其绝对耗时提高。修复后的辅助线程 CPU 和线程切换计数，比单看比例更直接地支持“逐消息跨线程交接开销已显著降低”。

剩余的可优化方向是后台校验中重复遍历/读锁、快照逐币查找以及行情与 TLS 处理。它们需要继续按绝对 CPU 收益评估；当前证据不足以承诺 Rust 在这些真实订阅与刷新工作量下比 Java 更省 CPU。本轮没有改变校验频率、缩减订阅或放宽新鲜度来压低读数。[修复后 perf 报告](../research/results/cpu-memory-fix-20260917/after-fix-profile-report.txt)、[采样栈](../research/results/cpu-memory-fix-20260917/after-fix-profile-stacks.txt.gz)、[上一轮诊断](cpu-latency-diagnosis-20260917.md)。
