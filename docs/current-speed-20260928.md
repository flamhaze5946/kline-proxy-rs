# Java 1.8.2 / Rust 0.4.15 线上接口速度 · 2026-09-28

东京测试机 192.0.2.10 对 market.feng.dog / market-mirror.feng.dog 的同条件 HTTPS 测量。采样于 19:26–19:30 UTC（迪拜 23:26–23:30），属于非整点、数据已就绪窗口。两套服务版本及 PID 与刚部署的产物一致。

## 日常接口

每个接口每端 1000 次正式请求，先各预热 20 次；每端复用一条 HTTP/1.1 连接，轮流交换请求顺序，每一对请求最短间隔 10ms。时间包括 HTTP 请求发送至完整读取响应体，JSON 校验放在计时之外；证书正常校验，使用固定实例 IP、正确 SNI/域名，Accept-Encoding: identity，不计 DNS。表中单位为 ms，p50 是中位数，p99 为最近秩法的第 99 百分位。

| 接口 | Java p50 | Rust p50 | Java p99 | Rust p99 |
|---|---:|---:|---:|---:|
| 合约单币 K 线，最近 10 根 | 1.57 | 1.21 | 2.23 | 1.59 |
| 现货单币 K 线，最近 10 根 | 1.46 | 1.19 | 2.25 | 1.67 |
| 合约 bulk，5 币 × 10 根，仅收盘 | 1.67 | 1.15 | 3.07 | 2.06 |
| 合约 bulk，5 币 × 10 根，含当前 | 1.73 | 1.25 | 3.28 | 1.88 |
| 合约全市场价格 | 1.94 | 1.38 | 4.07 | 2.14 |
| 现货全市场价格 | 3.03 | 1.78 | 13.35 | 3.53 |
| 合约单币价格 | 5.53 | 1.20 | 654.13 | 1.66 |
| 现货单币价格 | 20.86 | 1.13 | 137.59 | 1.67 |

全部 16,000 次正式常规请求返回 200 且数据结构校验通过。全市场价格的数量相同：合约 782 个、现货 3716 个；两端对应响应大小基本相同。单币 K 线为 BTCUSDT/1h，验证最近 10 根且包含当前小时；bulk 使用 BTC、ETH、BNB、SOL、XRP 的 USDT 交易对。

Java 单币价格接口会先调用 queryTickersBySymbols，经过共享限流器请求交易所 REST，然后才考虑内存兜底；合约权重上限为 35/秒，现货为 80/秒、单币查询权重 2。Rust 的对应查询优先读 WebSocket 实时缓存。本轮合约价格长尾约每 35 次出现一次，与 Java 固定一秒补充额度的限流方式一致；这是基于调用路径和时序的归因，未做逐请求线程栈采样，不能把每条等待全部精确分摊为限流或上游网络时间。

Nginx 上游耗时 p99：Java 合约单币价格 653ms、现货单币价格 137ms，Rust 两项均 1ms。慢段已出现在 Java 上游处理中，不能归咎于东京到 VPS 的网络。该差距包含缓存/REST 策略差异，不是纯语言比较。

## 200 个客户端，每个查询分散的 5 个 symbol

从两端共同已缓存的 732 个合约中确定性分组，每客户端 POST 查询 5 币 × 最近 10 根已收盘 1h K 线；每端 5 轮、每轮同时发起 200 请求，共 1000 次。Java/Rust 使用相同分组并交换测试先后顺序。每波覆盖全部 732 个币种，每个币种分配 1～2 次。各轮原始请求合并计算分位数，没有平均各轮 p99。

| 预热连接的 bulk | Java | Rust |
|---|---:|---:|
| 客户端 p50 | 69.10ms | 14.44ms |
| 客户端 p99 | 158.08ms | 28.41ms |
| 客户端最慢请求 | 172.66ms | 45.70ms |
| Nginx 上游 p99 | 151.00ms | 21.00ms |
| 整波完成时间中位数 | 138.71ms | 26.63ms |

Rust 客户端 bulk p99 比 Java 低 82.0%。两端共 2000 个请求均无错误、均有 5 × 10 根完整最新收盘数据，1000 对返回的 K 线字段完全一致。Java 1000/1000、Rust 999/1000 实际复用连接；Rust 一次重连仍保留在分布中（该次 TLS 约 42.9ms），没有删掉慢样本。

东京测试机有两个逻辑 CPU。复用组客户端 CPU 为 Java 各波约 26%～38%、Rust 约 107%～149%（100% 表示一核），客户端开销可能影响短时延分布；Nginx 上游 p99 同样从 151ms 降至 21ms，支持优势并非仅来自客户端差异。Nginx 时间精度为 1ms，0ms 表示舍入/精度范围内，不代表无开销。

## CPU 与内存

两台应用 VPS 均为两个逻辑 CPU，CPU 型号显示 Intel Skylake。以下为常规接口测试窗口的进程/服务资源；CPU 100% 表示用满一核，内存使用进程 VmRSS，未把 cgroup memory.current 当作 RSS。

| 指标 | Java | Rust |
|---|---:|---:|
| 应用平均 CPU | 16.6% | 10.5% |
| Nginx 平均 CPU | 3.2% | 2.2% |
| 应用 RSS 中位数 | 1975.2MiB | 585.3MiB |
| 应用 CPU 1秒采样峰值 | 47.5% | 18.8% |

采样包含 WebSocket、订正、持久化等后台任务及实例已有业务流量，不能当作每请求纯 CPU 成本。Java 采样器比第一条正式请求晚约 0.7 秒启动，两端实际统计窗口已写入 summary.json。

## 全新连接测试的限制

另做了每端 5 轮、200 条全新 TLS 连接的测试。原始客户端 p99 为 Java 2878.34ms、Rust 3794.48ms，但测试进程持续消耗约 198%～199% CPU，已经耗尽测试机的两个核心；握手/发送调度被同一个客户端限制，无法模拟分布在 200 个 Lambda 上的独立计算资源。这组原始数据完整保留，不用于判断应用服务性能，不能据此说 Rust 接口需要 3.8 秒。对应 Nginx 上游 p99 为 Java 9ms、Rust 1ms。

这次没有测量 Lambda 冷启动、HTTP/2、整点 final 帧等待、低流动性临时补零窗口，也没有覆盖所有业务接口。单币 ticker 在本次较密集调用下更容易触发 Java 的限流，低频请求的分布会不同。

测试后 Java 仍为 UP；Rust 2456/2456 就绪、14/14 连接有数据，stale_tail=0；两端没有自动重启。临时采样器已停止。
