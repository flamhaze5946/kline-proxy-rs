本轮排查确认：Rust 0.4.5 的内存优势保留，但较高的 CPU 有可定位的实现原因，主要集中在行情接收、跨线程调度、全市场快照生成和后台维护。普通 K 线查询还存在“返回 10 根、先复制全部历史”的额外工作。响应时间优势有限的原因需要分开看：应用本身已经很快的接口受传输开销限制，少数尾延迟则仍发生在服务端。

测量日期为 2026-09-17，时间均为 UTC。Rust 为 `192.0.2.40` 上的 0.4.5，Java 为 `192.0.2.30` 上的既有版本，东京客户端为 `192.0.2.10`。本轮没有部署应用改动或重启服务；在 Rust 实例安装了 `linux-perf`，运行了有时间上限的采样和请求测试。

CPU 的 100% 表示一个逻辑核心，两台服务实例均为 2 vCPU。RSS 是进程驻留内存，不是堆内存。

| 不带分析器的持续全市场价格查询 | Java | Rust |
|---|---:|---:|
| 应用 CPU | 8.03% | 22.35% |
| 其中用户态 / 内核态 | 6.17% / 1.86% | 16.04% / 6.30% |
| 平均 RSS | 2051.81 MiB | 841.22 MiB |
| 线程上下文切换 / 秒 | 814 | 4203 |

这次复测持续 90 秒，分析时排除最初 20 秒，各实例每 750 毫秒查询一次合约和现货全市场价格，使用本机 HTTP 长连接；Java 242 次、Rust 240 次请求全部成功。分析窗口分别约为 10:44:26–10:45:36 和 10:44:28–10:45:37。Rust 仍有约 59% 的 RSS 优势，但 CPU 是 Java 的约 2.78 倍。平均 CPU 占整台两核机器约 11.2%，这个实验不是容量上限测试。

两边并非完全相同的数据处理工作量：Rust 额外维护实时成交价格；Java 也继续承接生产请求。采样中 Java 的 ticker 指标只出现合约计数，不能将两者 CPU 差异直接归因于语言。复测窗口宿主机 CPU steal 为 Java 0.08%、Rust 1.10%，因此也不应把两个不同云实例当成严格相同硬件上的实验。

Rust 的分阶段实验把额外工作拆开了：

| Rust 状态，每段约 60 秒 | CPU | 成交消息 / 秒 | 现货 ticker 帧 / 秒 | 上下文切换 / 秒 |
|---|---:|---:|---:|---:|
| 无查询、无全市场成交订阅 | 11.43% | 0 | 278 | 1716 |
| 全市场成交订阅活跃，已经停止查询 | 17.70% | 695 | 250 | 4623 |
| 持续查询全市场价格 | 21.98% | 698 | 261 | 4706 |

这三段带相同配置的 perf 采样，不能与不带采样的数值当成严格配对结果；市场消息也在变化。不过，第二、三段成交消息速率接近，前两段快照发布数均没有增加，第三段合约和现货各发布约 10 次/秒。结合调用栈，可以明确区分成交订阅与快照维护的成本。阶段 CPU 差值分别约为 6.27 和 4.28 个百分点，是现场观测差值，不是承诺可全部消除的优化收益。

全市场合约价格查询会执行 `live.want(&[])`，订阅所有交易中合约的 `aggTrade`。请求停止后，兴趣保留 300 秒，订阅管理最长再经过一轮 60 秒检查才清理；快照维护则在最后一次请求约 5 秒后停止。这解释了为什么查询已经结束，CPU 仍可能继续偏高。相关代码见 [prices.rs](../crates/kline-market/src/ticker/prices.rs)、[live.rs](../crates/kline-market/src/ticker/live.rs) 和 [tickers.rs](../crates/kline-runtime/src/tickers.rs)。

调用栈中已经确认的热点如下。百分比表示一条 CPU 采样栈包含该操作的比例，包含下游调用；各项相互重叠，不能相加，也不是占整台机器的 CPU 百分比。

| 操作 | 无成交订阅、无查询 | 持续查询全市场价格 |
|---|---:|---:|
| ticker 消息处理 `ingest_connected` | 24.54% | 16.29% |
| 全市场快照编码 `encode_prices` | 0 | 17.42% |
| 分配 / 释放调用 `malloc`、`free` 等 | 17.63% | 16.13% |
| futex 同步相关调用 | 11.60% | 15.60% |
| 后台 `reconcile` 及其子任务 | 14.61% | 6.78% |

行情接收路径为“每帧创建任务 → Tokio 投递到辅助 CPU 线程 → 解析 → 通知 Tokio”。每条小消息都使用任务对象、信号量、同步队列和 oneshot；消息越密，唤醒与切换成本越大。解析又先构造 `serde_json::Value`，复制数组或对象，再创建展示对象、复制到不同缓存，并将小数字符串解析为 BigDecimal 后转回字符串。这些工作确实出现在分配、复制和同步栈中。见 [ticker.rs](../crates/kline-market/src/ticker.rs)、[cpu.rs](../crates/kline-market/src/cpu.rs) 和 [decimal 转换](../crates/kline-market/src/lib.rs)。

全市场快照把请求路径变快了，也把工作搬到了后台。现在以约 100 毫秒间隔编码合约 766 行和现货 3708 行，同时按约 500 毫秒的刷新目标维护 REST 基线。因此不能只看到前台返回缓存很快，就认为维护这个缓存没有成本。活跃窗口里 `encode_prices` 出现在 429 / 2462 条采样栈中，是明确的优化对象。

后台 `reconcile` 每 250 毫秒扫描全部序列，并在恢复任务完成时也进行检查；当前跟踪 2422 条序列。这里读取连接代次、缺口、尾部新鲜度和容量。它是持续的 CPU 消耗，并与 HTTP、WebSocket 共用 Tokio 运行线程。`fresh_tail` 本身只检查尾部至多两根，问题是频繁遍历所有序列和获取状态，不是每次检查全部历史。见 [lifecycle.rs](../crates/kline-runtime/src/lifecycle.rs) 和 [series.rs](../crates/kline-core/src/series.rs)。

普通 K 线查询有一个与用户使用方式直接相关的问题：[klines::cached](../crates/kline-market/src/klines.rs) 调用 `slot.records()`，复制该序列全部缓存，再按时间范围筛选，选中的 Bar 还会再次复制。实例的 1 小时序列保留 1001 根，日线保留 2001 根。因此返回最后 10 根仍有与全部保留数量成正比的复制成本，并在 Tokio 请求线程上同步执行。Java 对应查询使用有序映射的 `subMap` 取时间范围。这个实现差异已经由代码确认；本轮没有请求级 CPU 栈，不能声称某次 4 毫秒尾延迟全部由这一次复制造成。

响应时间测试同时比较三条路径：本机直接访问应用、本机通过 Nginx HTTPS、从东京通过 HTTPS 访问。每条路径、每个接口各 180 个正式样本；先运行 20 轮预热，正式轮次间隔 750 毫秒，交替请求顺序，保持连接，验证 TLS，关闭压缩。记录完整响应体接收耗时，JSON 解析放在该轮所有计时请求结束之后。

| 接口 | 应用直连 p50：Java / Rust | 本机 Nginx HTTPS p50：Java / Rust | 东京 HTTPS p50：Java / Rust |
|---|---:|---:|---:|
| 合约全市场价格 | 0.783 / 0.263 ms | 1.252 / 0.576 ms | 1.817 / 1.392 ms |
| 现货全市场价格 | 1.350 / 0.266 ms | 2.183 / 0.790 ms | 3.888 / 1.805 ms |
| 合约 bulk，32 币 × 10 根 | 0.773 / 0.599 ms | 1.299 / 0.518 ms | 1.943 / 1.345 ms |
| BTC 合约普通 K 线，10 根 | 0.584 / 0.289 ms | 0.824 / 0.487 ms | 1.401 / 1.274 ms |

这些是独立请求分布的分位数，不是同一个请求逐段打点，不能相减后当成精确分项耗时。本机请求还包括客户端、调度和内核网络成本，并不等于纯函数耗时；bulk 的本机 HTTPS 中位数低于直连，也说明不能机械相加。

全市场价格的应用直连中位数明显改善，但东京访问要叠加传输成本，剩余可优化的应用时间已经很少。例如普通 K 线在应用直连下相差约 0.30 毫秒，东京端中位数只相差约 0.13 毫秒。这类场景继续优化函数不会按比例缩短整个网络请求。

| 东京端接口 | Java 样本 p99 | Rust 样本 p99 | Java / Rust 最大值 |
|---|---:|---:|---:|
| 合约全市场价格 | 3.041 ms | 2.414 ms | 6.743 / 2.429 ms |
| 现货全市场价格 | 6.302 ms | 3.716 ms | 6.614 / 4.117 ms |
| 合约 bulk，32 币 × 10 根 | 4.661 ms | 3.734 ms | 4.799 / 3.757 ms |
| BTC 合约普通 K 线，10 根 | 2.194 ms | 4.096 ms | 4.858 / 5.232 ms |

普通 K 线的尾延迟问题仍存在。Rust 在 10:32:55 的东京请求耗时 5.232 毫秒，Nginx 记录 `request_time=4ms`、`upstream_header_time=3ms`、`upstream_response_time=3ms`。因此这一条不能完全归因于东京网络，应用或应用侧调度已经贡献了毫秒级等待。此接口的当前合约查询路径直接读内存，不经过 Binance REST 限流器。已确认的全历史复制、后台扫描和频繁线程唤醒都是可优化因素，但没有逐请求调度追踪，尚未把每个尾延迟分别归因到某个锁或任务。

正式样本共 4320 次，全部 HTTP 200、JSON 可解析；两端全市场价格的交易对集合一致，分别为 766 和 3708 个；bulk 都返回 32 个币种、每币 10 根且 `finalized=true`。测量时段约 10:30:28–10:33:00。Java 在同期还有 1529 条其他 Nginx 请求，Rust 为 0。固定间隔请求可能与周期任务相遇；每组 180 个样本的 p99 只反映少数慢请求，不能当作长期生产 p99 或容量结论。

建议按以下收益与实施成本顺序优化。此处是实施优先级，不是未经验证的收益承诺。

| 优先级 | 改动 | 预期作用与约束 |
|---|---|---|
| 1 | 普通 K 线按时间范围定位，只复制命中的记录 | 消除返回 10 根却复制 1001 / 2001 根的工作；保留起止时间包含关系、缺口和回退语义 |
| 2 | ticker / 成交使用类型化解析，移除整棵 JSON 的重复复制 | 降低长期后台 CPU、分配和释放；小数格式与精度必须保持兼容 |
| 3 | 小消息采用有界批处理或轻量处理路径，减少逐帧跨线程往返 | 减少唤醒、队列和同步成本；限制批次等待时间，维持单币价格新鲜度和顺序 |
| 4 | 全市场快照复用未变化的行或编码片段，减少重复格式化 | 优化已证实的 17.42% 采样热点；保留现有发布时效和独立的 REST 数据年龄限制 |
| 5 | 就绪检查增量更新，按变化与到期时间安排检查 | 减少反复全量扫描；连接断开、整点、缺口恢复仍须及时更新 readiness |
| 6 | 根据实际访问调整全市场成交订阅的保留时间 | 降低短暂查询后的后台消耗；需要权衡重新订阅成本与下一次查询的新鲜度 |

更换分配器、增加线程数可以作为后续受控实验。当前证据首先支持减少多余工作；尚无数据可以承诺将 CPU 降到 Java 的水平，或保证每个接口的 p99 都更低。
