**Rust 0.4.6 后续优化点分析 — 2026-09-17**

本轮在镜像实例采集了两组 60 秒 CPU 调用栈，并核对限流日志、2422 个持久化快照、内存结构尺寸和代码。线上仍为 0.4.6，PID 19605、自动重启 0，2422/2422 序列就绪。当前最有把握的新增机会是：按实际历史分配 K 线容量、修正小范围回填的请求 limit、减少后台重复校验工作。

以下按综合 ROI 排序，结合收益空间、实现范围及语义风险。收益空间是定位或模型结果，只有实施后重新测量才能确认实际降幅。

| 优先级 | 优化点 | 证据与收益空间 | 成本 / 风险 |
|---|---|---|---|
| 1 | K 线按实际历史逐步扩容 | 当前预留约 443.8 MiB；按快照数量建模可降至约 292.8 MiB，少预留约 151.0 MiB | 小 / 低至中 |
| 2 | 合约 REST 回填使用实际窗口 limit | 常规刷新配置 99 根，代码仍传 499；窗口不超过 99 根时，权重可由 2 降为 1 | 小 / 低至中 |
| 3 | 合并后台校验扫描，复用不变状态 | 活跃场景 reconcile 栈占 10.4%，无全市场价格访问时占 15.8%；每次回填完成及每 250ms 都全量扫描 | 中 / 中 |
| 4 | 优化价格快照逐币查找 | 快照拼接栈占 9.9%；每约 100ms 对完整列表执行字符串树查找 | 中 / 中 |
| 5 | ticker 缓存使用结构化对象 | 行情处理栈占 17.1%；当前仍为每条 ticker 构造带动态键的 JSON 对象 | 中 / 中 |
| 6 | REST 前台请求与后台维护分配优先级 | 慢队列日志中已有 1–4.19 秒等待；同市场高权重刷新与前台缺失请求共用 FIFO | 中至大 / 中至高 |
| 7 | 普通 K 线直接编码响应字节 | 仍先生成完整 JSON Value 再由 HTTP 层编码；可减少临时对象，尤其是较大返回量 | 小至中 / 低至中 |
| 8 | 闭合 K 线 bulk 的数据部分按版本复用 | 当前响应缓存固定 1 秒；相同已闭合数据仍可能反复编码，但现有样本命中率约 82.9% | 中 / 中，优先级较低 |

**1. 容量分配是本轮最大的内存机会**

[`Series::new`](../crates/kline-core/src/series.rs) 直接 `VecDeque::with_capacity(capacity.get())`。实例小时线配置上限 1001、日线 2001，许多新币的日线历史远少于这个上限。当前构造路径已申请整段缓冲区。

读取 2422 个 `.kpr` 的头部得到 2,165,226 根已保存记录。配置容量合计 3,635,422 个位置。将每条快照数量加一个形成中的 bar、再按上限封顶，并使用最少 64、之后倍增、最终不超过配置上限的模型，所需容量为 2,398,468 个位置。

同源码 Linux x86-64 布局探针确认 `Bar=96` 字节、`Entry=128` 字节。因此环形缓冲区容量模型为 **443.78→292.78 MiB**。这不等同 RSS 会下降 151 MiB：快照与实时状态有时间差，实际分配器、页面驻留和碎片也会影响结果。实现后应在全部数据就绪、缓存加载相当的情况下比较 RSS/PSS。

实现边界：保留配置上限、历史根数、精度、环形淘汰及乱序修正规则；使用受上限约束的增长策略，避免默认倍增超出保留容量。扩容发生在写路径，应预留合理起始容量并检查整点延迟。无需把存储、HTTP 或业务查询耦合在一起。

**2. 回填 limit 影响的是配额与等待**

[`Recovery::sync`](../crates/kline-runtime/src/recovery.rs) 的合约 `page_limit` 固定为 499，常规刷新仍把它作为请求的 `limit`。配置中的 `future_refresh_count` 为 99。实际返回数量受起止时间窗口约束，而配额权重由 limit 参数决定：官方规定 1–99 为权重 1，100–499 为权重 2。[Binance 官方 K 线接口规则](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/market-data#kline-candlestick-data)。

建议按每页实际时间跨度计算 limit。常规连续窗口可降到 99；较长缺口继续分页，月线、提前收盘、断线修复等边界仍按原规则校验。可减半的是**符合条件的合约回填请求权重**，不是整个程序 CPU，也不是全部 REST 配额。现货权重规则及冷启动长历史不能直接套用这个结论。

12:01–12:17 UTC 的日志记录了 35 个合约 K 线慢排队样本，中位数 2399ms、最大 2401ms；37 个现货样本中位数 3799ms、最大 4189ms。非 ticker 请求只有排队至少 1 秒才记录这些日志，因此这是一组筛选出的慢样本，不能拿它计算所有请求的平均等待或 p99。近期 K 线内存查询不经过这些 REST 队列。

**3. 后台校验存在重复扫描和重复读取**

[`reconcile`](../crates/kline-runtime/src/lifecycle.rs) 在定时 tick 和每一个完成的 REST 任务之后，都重新构造 feed token/epoch 数组并遍历全部序列。每条序列分别读取新鲜度和容量，多次读取时钟，再重建健康详情。`boundary_guard` 还会遍历所有序列的 interval，但当前配置实际只有 `1h`、`1d` 两种周期。

建议先实施容易验证的部分：复用 scratch 数组；仅在 feed epoch 或目录代次变化时重算映射；一把读锁获取容量及尾部状态；同轮复用时钟采样；合并同时完成的任务；将整点保护检查的周期集合去重。进一步改为增量调度时，需要保留严格的断线、缺口、到期检查和 readiness 语义，避免为降 CPU 延迟发现数据不完整。

回填自身还在开始和结束各复制一次整段 `slot.records()`。可以设计只读的“恢复计划/完整性摘要”，让恢复器在短锁内读取需要的信息，减少历史复制。不能把网络等待放进数据锁内。

**4–5. 快照索引与 ticker 数据模型**

[`Live::encode_prices`](../crates/kline-market/src/ticker/live.rs) 已复用编码后的行，但每轮仍按 symbol 从 `BTreeMap` 查行情；合约还需查 REST 时间水位。候选方案是内部哈希索引，或在基线变更时构建稳定 ID/索引，让 100ms 发布路径按索引取值。应先对照 benchmark；完整响应仍需拼接字节，不能把 9.9% 路径占比全部算成可消除的 CPU。

REST 列表必须继续定义完整覆盖和输出顺序，停牌/未知币种保留，连接断开、WS 过期及 REST 时间水位也必须继续生效。索引只属于行情缓存内部。

[`wire::Event::display`](../crates/kline-market/src/ticker/wire.rs) 仍创建动态 JSON Map，反复分配字段名称及节点。可将公开行情表示改为带可选字段的结构体，缓存继续共享 `Arc`，只在响应边界做序列化。相比仅优化解析器，这能进一步减少每条推送的对象分配；需要验证 FULL/MINI、现货/合约字段差异、null、数字字符串精度和返回字段类型。

**6. REST 调度主要针对冷路径长尾**

[`RestApi::acquire`](../crates/kline-market/src/transport.rs) 的 FIFO turn 覆盖整个等待，同市场回填、ticker 刷新和前台 REST 缺失查询共享调度。当前 1200 weight/min 的配置下，一个权重 40 的请求会把下一次准入推后约 2 秒，权重 80 推后约 4 秒。与日志中部分等待量级吻合，但尚未逐请求关联证明每个慢样本都由这类请求导致。

可在同一个总配额管理器内区分前台与后台，预留少量前台预算，并错开重型周期刷新。429/418 的共享冷却、取消、公平性和后台不饿死都必须保留。为不同请求类别直接各开一个完整配额池会破坏总预算约束。

这项主要改善需要 REST 的冷行情/缺失路径。已命中内存的近期 K 线和有效 WS 单币行情不需要排这条队列。由于会影响上游行为和公平性，放在前几项之后实施。

**低优先级与当前边界**

普通 K 线的 [`query`](../crates/kline-market/src/klines.rs) 在范围读取之后仍执行 `serde_json::to_value`，HTTP 层随后编码 JSON。直接生成响应字节可以减少中间对象；较大响应还应检查是否占用 Tokio 执行器过久。你通常只取最后 10 根，此项端到端收益预计比大响应场景小，尚未专项量化。

bulk 的全市场 revision 和 1 秒 TTL 还有优化空间，但实例累计 736 次 bulk 中已有 610 次缓存命中，且 `final_revisions_total=0`。这次证据没有显示“历史修正导致全市场失效”正在造成长尾。若延长闭合数据复用，应把 bar 数据与 `ts_ms` 等响应元数据分开，保留 forming 查询、目录变化、最终修正和整点切换的正确性。

本次 12:00 UTC 整点，合约 718/718 全部就绪约 164.01ms，现货 493/493 约 174.01ms；单条消息应用处理 p99 分别仅 0.0388ms、0.0274ms。当前整点到齐时间主要受消息抵达时序约束，继续优化解码不应被承诺能消除这百余毫秒。

TLS/I/O 栈在本次活跃采样出现约 22.3%，其中 AEAD/解密相关栈仅约 2.37%；其中还包含系统调用和内核网络处理。没有证据支持把更换 TLS 库或引入更复杂 I/O 框架列为优先事项。
