# 0.4.18 部署与回滚

0.4.18 补充多币价格查询的缺项兼容：交易规则中合法、但完整价格列表暂缺的币种，继续使用原有的排序基线刷新和单币查询路径，重复查询不会仅因排序表缺项而返回 503。该初始化路径仍受 5 秒查询上限约束。全市场价格的过期处理、后台预热和恢复调度沿用 0.4.17。当前部署与验证以 [长尾优化](long-tail-fix-20260929.md) 的最终二进制指纹为准。

0.4.17 将全市场价格持续刷新设为独立优先级，空闲时每 2 秒预热、活跃时仍以 500ms 为目标。价格刷新等待 1 秒后可借用每市场最多 120 权重/分钟（且不超过配置预算 10%）的平滑限速预留额度；总分钟配额与上游冷却不变。已建立的快照硬过期后不再等待 REST 刷新锁，明确返回 503；10 秒 REST 基线期限、250ms 编码期限和单币新鲜度保持原样。首次无快照的请求保留原有有界初始化行为。

新币初始化和连接恢复优先于例行订正，并提供最多一个额外恢复任务，避免所有普通 worker 被阻塞时新币排在其后。K 线订正周期、整点 guard、补零依据和持久化格式保持不变。`/health/ready` 仍检查完整订阅；新增 `/health/serving` 在首次完整就绪后检查已投入服务的序列，新币热身仍显示在严格检查中。启用 strict_readiness 时 bulk 按请求的币种和 interval 检查；请求全市场仍要求该周期完整。现有 strict_readiness=false 部署保持原业务可用性策略。回滚恢复 0.4.16 二进制即可。验证记录见 [长尾优化](long-tail-fix-20260929.md)。

0.4.16 的单币价格在 WS 行情不可用时，按配置周期顺序读取本地 K 线最新 close；本地命中绕过价格 REST 与限流器。缓存完全缺失时沿用原有回退。没有修改配置格式、磁盘格式、K 线补零条件及定时订正策略，回滚可恢复 0.4.15 二进制。合约本地取价 time 使用查询时刻，与 Java 一致；断线期间可能返回最后已知价格。实现和验证见 [单币价格缓存优先](single-price-memory-20260929.md)。

0.4.15 已在现货与合约启用严格基于上一根 WS `x=true` 的当前周期临时补零，取消因缺少当前 bar 等触发的即时 REST 尾部修复。规则与部署记录见 [当前周期补零](current-zero-bar-20260928.md) 和 [0.4.15 部署记录](current-zero-deployment-20260928.md)。

0.4.13 补齐 Java 接口兼容：配置周期顺序回退、多币行情排序、统计 HashMap 冲突顺序、参数绑定、K 线窗口边界、上游空响应与异常，以及 Actuator 和 HTTP 媒体协商。修复内容和 801 次严格业务差分、162 个 Rust 测试的证据见 [兼容性复核报告](api-parity-completion-20260928.md)。本次版本号递增不改变已验收的 Rust 源码。保持既有配置和持久化格式，回滚可恢复 0.4.12 二进制；无 symbol 的资金费率分块查询新增 1000 个小时块预算，超出返回 400/-1130。

2026-09-28 已部署至 `192.0.2.40` / `market-mirror.feng.dog`，2456/2456 条序列就绪，原生端口及公网各 43 项检查通过。切换时间、备份、源码指纹与在线 Java 对比见 [0.4.13 部署记录](parity-deployment-20260928.md)。

0.4.12 将统计 PNG 尺寸对齐为 Java 的 1024 × 768，并保留资金费率接口显式传入的空白 `symbol` 参数。`/health/ready` 新增 `unready_reasons`，分别显示初始恢复、连接代次、数据缺口和尾部新鲜度导致的未就绪数量；一个序列可能同时命中多个原因，计数不能相加作为未就绪总数。就绪判定规则没有改变。

0.4.11 修复持久化周期白名单、HTTP 输入兼容与 bulk 完成标记。升级已有配置时，依据实际生效的 Java `kline.persistence.{market}.intervalConfigs` 补入 `persistence.enabled_intervals`，不要重新覆盖已调优的历史容量和网络参数。缺省字段保留“所有周期允许持久化”的旧 Rust 行为；仅更新二进制不迁移白名单。新配置不能直接交给不认识该字段的旧版本，回滚必须同时恢复旧配置和旧二进制。详细契约见 [修复记录](compat-fix-20260918.md)。

0.4.10 显式设置 HTTP 监听 backlog，`listen_backlog` 缺省为 1024，旧配置省略该字段即可使用新默认值。此前 Tokio/Mio 在 Linux 上的默认值为 128；200 客户端同时建连时曾观测到监听队列溢出和约 1 秒的 SYN 重传长尾。1024 为这一负载提供约 5 倍的排队余量，不代表能够同时处理 1024 个业务请求。该项只影响等待 accept 的连接队列，HTTP 请求容量、行情同步与 Nginx 配置保持各自独立。Linux 会按 `net.core.somaxconn` 截断实际 backlog，部署后用 `ss -lntp` 核对监听端口的 Send-Q。扩大队列的效果以相同突发负载复测为准。

0.4.6 减少 CPU 与临时分配：普通 K 线以二分查找读取请求时间范围，保留缺口及默认窗口回退；行情推送借用 JSON 字段，24h ticker 的缓存共享不可变对象，标准十进制字符串直接保留原有精度与小数位数。4096 字节以内的行情帧在 I/O 任务内处理，每 32 帧主动让出执行权，大数组继续交给有界 CPU 池。价格行在更新时编码一次，全市场快照每约 100ms 拼接有效行；完整 REST 范围、连接断开失效、3 秒推送新鲜度、10 秒 REST 上限、250ms 编码快照上限及订阅寿命保持原有规则。运行中的服务升级及实测结果另见对应修复报告。

0.4.5 将全市场价格拆成独立的 REST 刷新和快照发布任务：活跃访问期间约每 500ms 刷新完整 REST 列表、约每 100ms 合入有效 WS 数据并发布预编码 JSON，请求复用不可变字节。批量编码只获取一次对应市场的读锁，避免逐币加锁和复制 JSON 树。停牌及元数据缺失币对保留在完整 REST 列表中，不要求它们拥有 WS 更新。REST 限流等待不会阻止发布 WS 新值。

全市场列表采用明确的过期上限：REST 基线最多使用 10 秒（此前超过 3 秒且 WS 未完整覆盖就等待 REST），编码快照最多使用 250ms；后台仍以 500ms 为 REST 刷新目标。只有冷启动或 REST 基线超过 10 秒才等待网络，沿用查询总时限 5 秒和超时 503，重新编码不会延长基线期限。`/health/market` 的各市场 `price_snapshot` 报告 REST/编码年龄、WS 覆盖行数、刷新和发布次数。该宽限会在上游排队时让未被 WS 覆盖的币对使用较旧 REST 值，不能将此延迟改善描述为等新鲜度加速。单币价格和 24h ticker 的 3 秒 WS 条件不变。

0.4.4 接通行情内存读取：单币 24h ticker 和现货最新价复用 ticker 推送；合约最新价按查询需求订阅 aggTrade，使用 p/T 返回价格与成交时间。订阅无访问 5 分钟后回收。推送连接断开立即失效，超过 3 秒未收到有效更新则使用 REST 兜底；合约时间顺序检查避免旧推送覆盖较新 REST 价格。全市场价格保留完整 REST 初始快照并合入推送，缺少推送的币种仍由后台 REST 维护，编码最多缓存 100ms。交易规则刷新期间可读最近有效快照，宽限最多两个配置刷新周期。REST 限速等待改为可取消的 FIFO，额度与冷却规则不变；ticker 查询的 5 秒总时限包含排队，超时返回 503。K 线容量、整点完整性与历史补齐范围保持现有配置。

0.4.3 增加价格查询和 REST 分段诊断：关联请求ID、元数据耗时、缓存加载归属、限速等待及竞争轮数、HTTP响应头/完整响应耗时。排队超过5秒时输出等待状态；行情数据、500ms缓存和限速调度算法保持原样，用于验证长尾来源。

0.4.2 将合约单币和全市场价格的 Binance 上游统一为 `/fapi/v2/ticker/price`，与 Java 一致；单币权重为 1，全市场权重仍为 2。调用方继续使用 `/fapi/v1/ticker/price`。现货仍使用 `/api/v3`，合约 24h ticker 仍使用 `/fapi/v1/ticker/24hr`。此次保留现有 500ms 缓存与 REST 调度行为，因此不能仅凭版本切换认定秒级长尾已消除。

0.4.1 修复历史停牌日提前收盘被误判为数据缺口的问题：固定周期按相邻开盘时刻校验连续性，保留上游原始收盘时刻，并继续拒绝真实缺口与重叠。整月周期沿用真实月界。

固定内存容量包含形成中的 K 线。如果业务需要完整返回 1000 根已收盘 1h K 线，容量与磁盘保留数至少设为 1001；2000 根已收盘日线则至少 2001。Java 当前有额外 50 根的批量裁剪缓冲，不能仅按相同容量字段推断两端实际保留数量相同。2026-09-17 镜像部署采用 1001 / 2001，并在就绪后校验同一截止时间的返回数量与内容。

先在独立端口验证，再选择业务切换窗口。现有 Java 服务和 Nginx 不由构建、配置转换、对照脚本自动修改。

## 构建与配置

macOS 本机：`./scripts/check.sh`。Linux x86：安装 Rust 1.92 的 `x86_64-unknown-linux-gnu` target、Zig、cargo-zigbuild 后，运行 `sh scripts/build-linux.sh`。目标最低 glibc 2.28；内置 Noto Sans 字体，PNG 不依赖主机字体或 Fontconfig。分发时携带 `LICENSE-NotoSans.txt`。

```sh
python3 scripts/convert_java_config.py /path/to/application.yaml \
  --output /path/to/config.json --java-root /opt/kline-proxy \
  --listen 127.0.0.1:1889 --data-dir /var/lib/kline-proxy-rs
./target/release/kline-proxy --check-config /path/to/config.json
python3 scripts/package-release.py
```

转换器读取嵌套与点分 YAML 键，保留订阅正则、continuous 选择、周期容量、资金与统计默认行为，并转换 Java 持久化配置。支持 double、float、string、bigDecimal，未指定时采用 Java 的 bigDecimal 默认值。详细映射和不能直接复制的运行时参数见 [配置迁移](config-migration.md)。环境变量覆盖应先合并进输入配置，不能只转换未生效的仓库模板。

Java 开启持久化时，实际维护容量是 `max(minMaintainCount, maxStoreCount)`；转换器保留这个规则。例如现货 1h 的 18000 根和 BTCUSDT 的 20000 根不会退化为 9000 根。Rust 内存和磁盘限制可分别配置，磁盘大于内存时合并已存历史；若要首次从 REST 就备齐更长历史，内存容量也应设为目标深度，或导入已有 Java 快照。

`legacy_directory` 只读 Java JSON；`directory` 必须使用独立 Rust 目录。设置 systemd 用户、目录权限和配置文件后再安装 `deploy/kline-proxy-rs.service`。示例单元只允许写 `/var/lib/kline-proxy-rs`。运行时目录不要由两个 Rust 进程同时使用。

## 影子验证

完整市场 1h=9000、1d=1000 的冷加载涉及大量历史 REST 分页；先导入快照，或在独立环境完成加载。每进程 REST 权重预算并不感知同一出口的其他进程，应给 Java 和 Rust 留出合计配额。

同机并行时先核对空闲内存，给影子服务使用较短历史，避免同时挤占 Java 的 CPU、磁盘与出口配额。就绪需要所有配置序列恢复完成，且每条 WS 连接收到对应数据；仅进程存活或端口打开不够。

```sh
curl -fsS http://127.0.0.1:1889/health/ready
python3 scripts/shadow_compare.py \
  --java-url http://127.0.0.1:1888 --rust-url http://127.0.0.1:1889 \
  --hours 2 --output shadow-results.jsonl
curl -fsS http://127.0.0.1:1889/health/performance
```

对照脚本只发只读请求，按同一截止时间比较合约和现货的已收盘历史。保留原始响应与差异；不把当前形成中 K 线的自然变化算作错误。它不复现 Lambda 负载，也不构成线上 p99 基准。正式切换前应覆盖至少两个整点、真实订阅规模、Nginx/TLS 路径和实际 Lambda 并发，并检查缺失、pending、429、CPU、RSS 与历史覆盖。

## 切换和回退

记录当前 Nginx upstream、Java unit、配置与快照位置；保留 Java 运行或可立即启动。完成影子检查后，在既有非整点窗口修改 upstream 端口，执行 `nginx -t` 成功后 reload。观察真实请求错误率和收盘就绪情况。

异常时把 upstream 恢复到原 Java 端口，重新 `nginx -t` 和 reload；Java 使用原目录，不读取 Rust `.kpr`。停止 Rust 使用 SIGTERM，给 HTTP 最多 35 秒排空，再写最终快照；单元停止超时为 90 秒。不要把清理 Java 快照或删除旧二进制并入切换流程。

本版本的代码移植、构建和隔离测试不等于已经完成生产切流；实际执行情况以 `research/results/migration-*.json` 的环境、二进制指纹和时间为准。
