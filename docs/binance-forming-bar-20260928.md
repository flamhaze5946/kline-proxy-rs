# 币安未推送当前 K 线时的官方 REST 行为

后续更新：[跨 1m 边界及 UTC 18:00 的 1h 整点实测](binance-zero-volume-1m-20260928.md)已经确认，官方 REST 会出现当前零成交量 bar，现货 WS 也观察到这类主动推送。下文保留最初小时中段采样的原始结论和局限。

2026-09-28 第一轮实测发现第三种情况：**观察期间没有收到 K 线 WebSocket 消息，但官方 REST 已有本小时非零成交量的 bar。** 不能把“目前没有新推送”直接解释成“本小时没有成交”。

本轮在小时中段完成，不能单独回答刚换小时、尚未收到第一条当前小时消息时是否有零 bar。随后完成的 UTC 18:00（迪拜 22:00）整点采样已经证实存在这种返回值；结果及证据见本报告末尾和后续报告。

## 方法和观测范围

- 地点：用户提供的东京测试机 `192.0.2.10`。
- 观察：UTC 17:35:44.780 至 17:37:36.933，共 112.152 秒；目标 bar 为 UTC 17:00–17:59:59.999。
- 订阅：732 个 USDT 合约、496 个 USDT 现货，共 1,228 个交易对，9 条独立官方 WebSocket 连接。
- 每条连接都有订阅成功 ACK 及 BTCUSDT 活跃对照，未发生连接错误。合约每条连接观察到 217 条 BTC K 线消息，现货每条连接 56 条。
- 首先选择 20 秒内未收到本小时消息的币种，查询官方 REST 最新两根 1h K 线；对之后仍静默的币种再查询一次。查询期间继续接收 WS，把请求过程中已收到消息的币种排除。
- 最终表格使用更严格条件：**整个 112.152 秒窗口内一条 K 线消息都没收到**，且有成功的两轮 REST 证据。
- 调用的是币安官方公共行情 API，不是代理服务，也不是官网网页图表截图；探针连接独立于生产连接。

## 已完成结果

| 市场 | 订阅币种数 | 全程无 K 线消息 | REST 末根为上一小时 | 当前小时零成交量 | 当前小时已有成交 |
|---|---:|---:|---:|---:|---:|
| USDT 合约 | 732 | 31 | 0 | 0 | 31 |
| USDT 现货 | 496 | 71 | 0 | 0 | 71 |
| 合计 | 1,228 | 102 | 0 | 0 | 102 |

这 102 个币种两轮 REST 的当前小时 bar 完全相同。因此，结果与“两次请求之间没有新成交、但本小时较早已有成交”相符。它不能证明从整点开始没有推送，也不能替代对生产连接是否丢消息的调查。

其中 HK0625USDT、BITOUSDT 也曾出现在此前 17:00 生产 `stale_tail` 的样例中；这只是币种交集，不代表此刻新建立的探针连接重现了整点时生产连接的全过程。

按“截至第二轮 REST 返回仍未收到当前小时消息”这一较宽条件，合约有 47 个、现货 83 个，共 130 个，全部是本小时已有成交。部分随后收到 WS，因此表格只保留全程静默的 102 个。

首轮候选为 347 个；第一轮 REST 查询结束后剩 164 个进入复查；130 个直到各自复查响应时仍静默，最终 102 个持续静默到整个观察结束。这些是不同时间点的筛选结果，不应互换分母。

## 对补零策略的含义

用户提出的“先用前一根已确认 close 构造当前 bar，成交量和成交笔数为 0”可以作为临时占位策略；本轮实测说明它不能被视作官方真实数据。没有 WS 消息时，官方 REST 可能已经有该小时较早成交的真实 bar，所以占位必须继续允许真实 WS/REST 数据替换，且不能冒充已确认收盘数据，也不能因为有占位而停止真实数据的补全。

Java 的独立受控调查已完成 18 个场景：普通 1h 单币请求默认只读内存，不指定时间范围时会返回最近的旧 bar；bulk 也不自动向尾部创建当前小时零成交量 bar。Java 现有补零是在已观察到的两根 bar 之间补缺口。完整 Java 调查位于 Java 仓库 `docs/java-missing-forming-20260928.md`。

## 后续整点证据已补齐

UTC 18:00 的探针已在整点前建好连接，完成 +10 秒起的初查和 +60 秒起的复查，原始证据校验通过。合约初查发现 15 个在没有当前小时 WS 时返回本小时零成交量 bar 的样本，复查仍有 8 个；现货 WS 观察到 373 个 symbol 的当前小时零成交量 bar。详见[后续报告](binance-zero-volume-1m-20260928.md)及其中的 1h 原始证据链接。
