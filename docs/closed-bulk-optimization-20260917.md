**Rust 收盘与 bulk 优化交付报告 — 2026-09-17**

8 项优化已实现并部署至 `market-mirror.feng.dog`，最终版本 **0.4.9**。
Java 实例未修改。结论是：收盘消息处理与 bulk 构建的 CPU 热点明显减轻；
内存占用下降，但**常驻 CPU 和端到端 p99 尚未获得稳定改善，不能称为全部性能问题已解决**。

部署时间 2026-09-17 14:24:21 UTC（迪拜 18:24:21）；PID 23313，NRestarts=0。
最终检查：2422/2422 序列 ready，14/14 WebSocket 流正常，配置 SHA256 保持不变。

| 优化项 | 已完成的行为 | 关键约束/验证 |
|---|---|---|
| 1. 收盘诊断移出接收路径 | 有界队列收集样本，后台聚合；定时核对成员 | 使用接收/提交时刻计时；诊断丢样计数 0，行情数据不丢弃 |
| 2. 最近闭合行预编码 | 响应层准备最近 10 根；按请求最多缓存 100 根，重复利用未变化的 JSON 行 | 新条目、close time、final、历史修正、裁剪、目录变化均正确失效 |
| 3. reconcile 扫描减负 | 固定 250 ms 巡检；连接映射复用、合并状态锁；REST 完成只从待办队列补任务 | 不再每条 REST 响应触发全目录扫描；历史刷新仍为 300 秒 |
| 4. 按版本复用 bulk 正文 | 每序列版本校验；正文跨 1 秒响应缓存 TTL 复用 | 元数据包装保留原有 TTL；时钟回拨和已完成旧 single-flight 不能返回过期数据 |
| 5. 独立 bulk 构建队列 | 默认 2 个专用线程、有界任务；最多一个大请求同时构建，为小请求留出工作线程 | 同键请求合并；取消、panic 后恢复及公平性回归通过 |
| 6. 最新 final 优先补齐 | 通常整点后 500–750 ms 发现缺失；仅回填最新 2 根；WS 已补齐则取消等待 | 共用市场配额、滚动窗口和 Retry-After；不能绕过限流或把整段历史直接标 ready |
| 7. 普通 K 线直接编码 | 内存数据直接生成 JSON 字节，减少中间 Value 树 | 4 种数值模式、原始时区/月线透传保持契约 |
| 8. 历史按实际数据分配 | 初始空序列不预分配完整历史；验证后的批次一次预留实际条数加最多 32 根余量 | 根数上限不变；修正逐根扩容产生的 RSS 碎片回退 |

`reconcile` 是后台核对、恢复和调度器。250 ms 扫描检查的是本机内存状态，
并不意味着每 250 ms 请求 Binance。WebSocket 入库和 bulk 等待唤醒均由事件触发，
不等待巡检。这个周期保留了约 250 ms 的异常发现粒度，并非业务必须值。

**同机受控测试：0.4.6 → 0.4.9**

在东京测试机交替运行两版，5 轮；相同输入、相同保留上限。
下表为应用内部测量，不含交易所发送时间、HTTP、Nginx、TLS 和网络。
bulk 已预热每行数据，关闭整包响应缓存，测的是重新构建响应；不是普通热缓存命中。

| 指标 | 0.4.6 | 0.4.9 | 变化 |
|---|---:|---:|---:|
| 720 条模拟收盘消息处理批次 p50 | 26.082 ms | 2.020 ms | 降低 92.3% |
| 32 币 × 10 根 bulk 构建 p50 | 0.740 ms | 0.044 ms | 降低 94.0% |
| 720 币 × 10 根 bulk 构建 p50 | 14.691 ms | 0.586 ms | 降低 96.0% |
| 混合历史内存测试 RSS | 89.02 MiB | 87.73 MiB | 降低 1.5% |

收盘批次各 100 个样本；两种 bulk 分别各 1500、750 个样本。
把后台诊断排空也计入，收盘批次平均耗时仍由 24.44 ms 降至 2.86 ms，
不是只把计算隐藏到另一个线程。内存测试为 1000 个序列、上限 2001 根，
实际历史为 20/99/365/800/2000 根各 200 个；新版使用生产恢复路径的批量预留提示。
实际 RSS 仅小幅下降，先前仅按“预留容量”估算的节省不能当作物理内存收益。

**最终实例接口测量**

2026-09-17 14:31–14:33 UTC，每组 500 个计时样本、20 次预热；长连接 HTTP/1.1，
identity 编码，完整读取响应体后停止计时，JSON 解析在计时外。共 6000 次请求全部成功，
每次检查最新收盘时间、根数和 pending，12 组抽样业务数据与 Java 完全一致。
Java 没有现货 bulk 路由，未将其错误响应混入性能比较。

| 接口/链路 | Java p50 / p99 | Rust 0.4.9 p50 / p99 |
|---|---:|---:|
| 实例直连 · 合约 bulk 32×10 | 0.971 / 3.651 ms | 0.411 / 3.050 ms |
| 实例直连 · 合约 BTC 最近 10 根 | 0.600 / 1.041 ms | 0.264 / 1.376 ms |
| 实例直连 · 现货 BTC 最近 10 根 | 0.724 / 1.299 ms | 0.347 / 2.167 ms |
| 东京 HTTPS · 合约 bulk 32×10 | 2.112 / 5.236 ms | 1.518 / 6.975 ms |
| 东京 HTTPS · 合约 BTC 最近 10 根 | 1.442 / 1.985 ms | 1.232 / 8.827 ms |
| 东京 HTTPS · 现货 BTC 最近 10 根 | 1.545 / 2.271 ms | 1.293 / 5.385 ms |

这一轮 Rust 的中位数更低，但 HTTPS p99 高于 Java。上一轮优化构建的 6000 次探测中，
Rust 合约 bulk 直连/HTTPS p99 为 0.749/2.175 ms，Java 为 3.748/5.107 ms。
两轮差异很大，因此不能只选择较好的那轮声称线上长尾已经解决。

应用内合约 bulk 1172 次记录 p99 为 0.228 ms、最大 1.711 ms；
126 次实际构建中，等待 final 的 p99 桶上界 0.05 ms，构建排队 0.2 ms，编码 0.5 ms。
正文实际生成 4 次、按版本复用 122 次；整包缓存命中 1050 次。
这些统计的样本集合和计时边界不同，不能与客户端 p99 直接相减。
它们支持“缓存和构建成本已下降”，但还不足以把客户端剩余尾延迟唯一归因到某个 I/O/TLS 环节。

**资源观测与限制**

各 60 秒，合约/现货全市场价格各约 0.75 秒请求一次。
CPU 以一个逻辑核心 100% 计；Rust 两轮均启用 199 Hz perf 采样。

| 实例/版本 | 平均进程 CPU | 平均 RSS | 现货 ticker / 合约 trade 消息每秒 |
|---|---:|---:|---:|
| Rust 0.4.6 | 18.93% | 751.8 MiB | 420 / 1066 |
| Rust 0.4.9 | 24.02% | 500.9 MiB | 471 / 1933 |
| Java | 13.42% | 2051.8 MiB | 未取得相同口径 |

新版采样时合约成交消息约为基线的 1.81 倍，现货 ticker 约为 1.12 倍；运行时长也不同。
资金费率缓存基线 334 小时、新版 329 小时。因而总 CPU/RSS 是观测结果，不能全部归因于代码。
较早一轮新版 CPU 为 19.18%，与基线 18.93% 基本持平；最终这轮升到 24.02%，
目前没有证据可以保证常驻 CPU 已下降，仍高于 Java。
最终采样中 Tokio 线程合计约 20.78% CPU，行情计算线程约 3.18%，bulk 线程接近空闲。
下一处剩余瓶颈应从行情消息处理、网络事件调度与客户端长尾的同请求关联继续定位，
不能再把全部问题归因于 bulk JSON 编码或 REST 限流。

**回归与复查**

98 项 Rust 测试、7 项 Python 配置迁移测试、fmt、Clippy `-D warnings`、macOS 和 Linux
release 构建通过。最终实例另做 241 次请求回归，其中 128 次 bulk 请求、并发 16，全部成功；
合约和现货各保留 1000 根小时线、2000 根日线的查询结果。CPU 符号副本验证了所有 ELF
已分配段及地址与部署二进制完全一致，分析副本不替换在线进程。

复查修正了新 forming 插入、close time 提前变化、删除后重新添加序列、历史修正、时钟回拨、
取消/并发唤醒、逐根扩容碎片，以及周/月线固定查询边界与上游开盘网格不一致的问题。
未通过减少历史根数、延长过期数据有效期或伪造 final 来获取测试收益。

14:00 UTC 的整点实盘样本采自部署前的 0.4.6，不能当作 0.4.9 整点效果。
本报告中的新版收盘加速是同机受控处理测试；新版下一次实盘整点尚未在本报告中验证。
