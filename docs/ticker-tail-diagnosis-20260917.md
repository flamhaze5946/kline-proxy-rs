# Rust 价格接口长尾排查：缓存未命中后的本地限速等待

2026-09-17，实测窗口 06:40:00–06:41:39 UTC（迪拜 10:40:00–10:41:39）。

已确认：本轮复现的合约单币价格长尾，主要发生在缓存未命中后等待进程内 REST 限速额度的阶段。两笔成功请求分别耗时 11.328 秒、10.016 秒，其中排队占比均超过 99.9%；实际 Binance HTTP 请求约 3ms，首次请求即返回 200，没有重试或 429/418 冷却。另有一笔请求因排队持续过久，在 Nginx 等待约 60 秒后返回 504。

结论范围是 `market-mirror.feng.dog/fapi/v1/ticker/price?symbol=BTCUSDT`；上游已使用 `/fapi/v2/ticker/price`。不能把本次结论直接推广到所有 bulk、统计和资金费率接口，也不能逐毫秒还原此前缺少分段日志的 52.112 秒请求。

## 实测证据

从独立东京测试机 `192.0.2.10` 请求 Rust 镜像 `192.0.2.40`。每组先间隔 750ms，使 500ms 价格缓存过期，再发价格查询；成功后立即重复同一查询检查缓存命中。请求串行、HTTPS 证书校验开启、连接复用，共 20 次过期后查询和 19 次紧随其后的命中查询。

| 样本（query_id） | 客户端总耗时 | 本地限速等待 | Binance HTTP 全部响应 | 等待轮数 | 结果 |
|---|---:|---:|---:|---:|---|
| 7 | 11,327.7ms | 11,321.2ms | 3.33ms | 112 | 200 |
| 9 | 10,015.6ms | 10,007.7ms | 3.03ms | 99 | 200 |
| 11 | 60,027.4ms | 至少 57,029.7ms | 未见取得额度或发送阶段记录 | 至少 548 | Nginx 504 |
| 36 | 1,680.8ms | 1,674.7ms | 3.22ms | 1 | 200 |

样本 7、9 的元数据校验耗时分别为 0.97ms、1.16ms，均有 `load_owner=true`，直接证明这两笔请求发起了价格缓存加载。它们之后的缓存命中请求分别只耗时 1.78ms、1.88ms。所有成功的过期后查询也都匹配到缓存加载记录。

样本 11 在 06:40:26.287 开始缓存加载；最后一条等待日志在 06:41:23.317，记录 `queue_ms=57029.731491 rounds=548 cooldown_rounds=0`，之后未出现取得额度、HTTP 响应头或加载成功日志。Nginx 于 06:41:26 记录 `504 rt=60.025 uct=0.000 uht=- urt=60.026`。57.030 秒是日志直接证明的等待下界，不能写成精确的最终排队时间。

20 次过期后查询：19 次成功、1 次 504；成功请求中位数 5.90ms，有 3 次超过 1 秒。19 次缓存命中全部成功，中位数 1.88ms，最大 3.66ms。这是用于定位原因的小规模定向采样，不是生产 p99 或错误率估计。

开始测量前，06:39:54 就绪状态已经达到 2422/2422，14 条连接全部有数据。测量期间及之后的 18 个健康样本均保持就绪，后台 `rest_jobs=4`；没有将重启恢复阶段样本混入上表。Nginx 39 条记录与客户端 39 次请求按顺序、完成时间和状态全部对齐。

## 为什么会发生

1. 单币价格缓存 TTL 为 500ms，过期后通过 Moka `try_get_with` 加载 REST 数据。相同键的并发未命中会共享一次加载，因此一个加载任务长时间等待时，其他同币种请求也可能一起等待；本轮串行探针没有额外测量这种并发传播。
2. 价格查询、元数据和后台 K 线补齐/校验等调用共享一个 `RestApi`；其中合约调用共用同一限速通道。配置未覆盖默认预算，使用每市场 1200 权重/分钟，后台恢复并发为 4，每条序列默认每 300 秒再次校验。数据就绪不代表后台 REST 已停止。
3. `acquire()` 没有维护先来先服务的队列。请求检查共享截止时间后释放锁并休眠；醒来时重新竞争。另一请求取得额度后会继续推迟截止时间，旧请求可能连续数百次竞争失败。短暂互斥锁的公平性不能保证整个限速等待过程的公平性。样本 7、9、11 的等待轮数直接显示了这种反复等待。
4. 15 秒超时设置在 HTTP 客户端上；`acquire().await` 在发送 HTTP 之前，所以排队不包含在该超时内。持续排队最终触及 Nginx 等待超时，产生 504。

这些样本的 `cooldown_rounds` 全部为 0，成功请求均为 `attempt=0/status=200`。本轮证据支持普通本地额度等待及调度饥饿，不支持将它们归因于 Binance 429/418 冷却、HTTP 重试或上游价格响应耗时。

还有一个后台额度放大点：配置的 `future_refresh_count=99` 决定了回看起点，但非冷恢复请求仍把固定 `page_limit=499` 传给合约 K 线接口。传输层因此使用权重 2，而 `limit<100` 对应权重 1。应在保留缺口补齐、分页和历史覆盖语义的前提下，按实际请求时间区间计算 limit；不能直接把所有分页统一改为 99。这个问题由部署源码与配置确认，本次未单独做其收益对照实验。

## 建议修复顺序

| 优先级 | 修改 | 目的与约束 |
|---|---|---|
| 1 | 公平且可取消的限速排队；在共享总预算内给前台请求保留服务份额或有限优先级 | 消除反复抢额度导致的饥饿；后台仍须持续获得服务，429/418 冷却仍必须全局生效 |
| 2 | 根据实际补齐范围缩小 K 线请求 limit，并避免不必要的重复补齐 | 降低后台消耗；用缺口、长时间断线和历史覆盖测试验证行为 |
| 3 | 给请求设置包含排队、重试和 HTTP 的总时限，并正确取消等待任务 | 控制失败时的最长等待；这是保护措施，本身不能使成功请求变快 |
| 4 | 评估主动刷新或允许旧值的缓存策略 | 进一步减少前台 miss；需要明确价格新鲜度约束，不能靠直接延长 TTL 掩盖调度问题 |
