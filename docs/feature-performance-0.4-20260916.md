# Java 与 Rust 0.4 各功能性能对比报告

测量日期：2026-09-16，19:05:58–19:09:46 UTC（迪拜 23:05:58–23:09:46）。当前 Mac 本机受控实测；本轮没有切换或压测生产实例。

**主要收益是 CPU、内存和数据就绪后的查询。等待行情的整点 bulk p99 与 BigDecimal 统计中位耗时基本持平。**

热 bulk p99 下降 59.6%；100 / 1000 根 K 线查询 p99 下降 21.7% / 25.0%；常规回放每轮 CPU 时间下降 78.0%。这些结果不等于真实 Nginx/TLS/Lambda 链路的收益。

## 数据就绪后的 HTTP 查询

| 功能 | 并发 | 样本/实现 | Java p50 ms | Rust p50 ms | Java p99 ms | Rust p99 ms | p99 变化 |
|---|---|---|---|---|---|---|---|
| K 线 bulk · 6 标的 × 1 根 | 96 | 15360 | 1.075 | 0.820 | 3.219 | 1.299 | 下降 59.6% |
| 普通 K 线 · 100 根 | 96 | 15360 | 2.541 | 2.182 | 5.413 | 4.239 | 下降 21.7% |
| 普通 K 线 · 1000 根 | 32 | 5120 | 8.088 | 5.918 | 15.022 | 11.269 | 下降 25.0% |
| 服务器时间 /time | 96 | 15360 | 0.625 | 0.538 | 1.248 | 0.664 | 下降 46.8% |

数据已就绪；合约 double；718 标的 × 2 周期 × 1000 根。回环 HTTP/1.1 长连接，两端 TCP_NODELAY。每进程每接口先 80 轮预热，再 80 轮测量；两次进程 AB/BA。记录请求发出至完整响应体收完；JSON 验证在计时后执行。Java 使用 JDK HttpServer 适配器调用真实服务/Jackson，并非生产 Tomcat；Rust 使用真实 Axum 路由。单机 Python 客户端也影响延迟；无 TLS、Nginx、Lambda。热查询指数据就绪且预热完成，并非保证响应缓存 100% 命中。HTTP/统计独立 Cargo harness 用默认 release profile；回放用工程 release profile（thin LTO、1 codegen unit）。每请求验证状态、条数、最终性和收盘值，两边响应字节数一致。

整点等待型 bulk 合并 p99 为 **126.058 → 126.245 ms（增加 0.15%）**。Java 两次进程 p99 为 132.392 / 124.827 ms；Rust 为 126.035 / 126.348 ms。小差异随运行可反向，没有稳定改善证据。计划最晚最终帧在 +131 ms 注入，处理器无法提前获得尚未到达的数据。

接收至提交从程序接收边界开始，Java 包含内部队列、Rust 直接提交；不包含接收前的网络或输入调度等待。flood 的整点偏移下降 41.0%，但加回开始注入的 20 ms 后，完整批次完成耗时只下降 25.4%，不能混用分母。

## Yama01 + Yama02 统计计算

| 模式 | Java p50 ms | Rust p50 ms | Java p95 ms | Rust p95 ms | p50 变化 |
|---|---|---|---|---|---|
| Yama01 + Yama02 · double | 4.368 | 3.397 | 5.867 | 3.544 | 下降 22.2% |
| Yama01 + Yama02 · bigDecimal | 0.946 | 0.957 | 1.048 | 1.117 | 增加 1.1% |

每样本 64 标的 × 65 天，days=1、volumeDays=1、rank=20；合计计算 Yama01 和 Yama02。每进程每模式预热 30 次、测量 50 次，两进程合并 100 次。只计真实计算方法，不计输入解析、HTTP、缓存、PNG、ATR 或聚合接口。夹具对应先前差分 case 1/121，260 个输出点一致，本次每次结果均 130 点。Java 有反射调用边界，Rust 有 black_box 防消除。每模式仅一个输入集合，不代表所有统计窗口；double 与 BigDecimal 内部算法不同，不能由此推断通用模式快慢。样本较少，以中位数为主要结论，补充 p95。

double 中位数下降 22.2%；BigDecimal 中位数增加 1.1%，基本持平。只有两个进程、每模式一个数据配置，不认定 1.1% 为稳定退化；不能据此比较不同数值模式的通用性能。

## 测量方法

| 项目 | 口径 |
|---|---|
| 主机 | Mac17,6 / macOS-26.5.2-arm64-arm-64bit-Mach-O / 18 逻辑 CPU / 128 GiB；同机顺序执行，无 CPU 绑定。 |
| 版本与资源 | Java 21.0.8，-Xms1g -Xmx2g -XX:ActiveProcessorCount=2；Rust 0.4.0 release，Tokio 2 workers。Java 消息工作线程为 4；这不是相同 2 核配额实验。 |
| 构建配置 | 回放使用工程 release profile：thin LTO、codegen-units=1；HTTP/统计独立 harness 使用 Cargo 默认 release profile。均链接当前 0.4 源码，未直接测试完整部署二进制。 |
| 运行顺序 | 两次独立进程：先 Java→Rust，再 Rust→Java。只汇总预热后的样本；Java 仍可能继续 JIT/GC，未做冷启动性能比较。 |
| 分位数 | 从两轮原始样本重新计算，p50 中位数，p95/p99 nearest-rank。原始 summary.json 使用旧 floor(N*p) 下标，仅作单轮日志；最终 comparison.json 与报告统一使用本口径。 |
| 正确性 | 1200 个回放轮次（含预热）均收到 1208 个最终提交，缺失/错误收盘/错误形成中/未最终 bulk 均为 0；HTTP 所有请求验证通过；统计夹具原差分 260 点相等。 |
| 适用范围 | 受控合成输入的真实测量；不包含生产 Nginx/TLS、Lambda、公网行情、完整后台混合负载。仅两次进程，无置信区间或显著性承诺。 |
| 历史证据 | 2026-09-15 Linux ARM64、Rust 0.1 数据仅作历史资料，不与本轮 Mac / 0.4 混算；0.3 的实例检查也不能替代 0.4。 |

## 下一步优先级

1. 实例完整容量影子对照至少两个整点：同请求组合、连接复用、后台功能，关联 bar-close、最后消息接收、应用 bulk、Nginx request_time/upstream_response_time、CPU/RSS 与错误率。
2. 资金冷/热缓存、整点预热及 :05 重试与 K 线混合压测，验证异步加载与 CPU 隔离。
3. 再按真实流量补测 ticker、PNG、落盘和恢复。不能用核心 K 线收益替代这些功能的证据。

连续缓存、减少分配、共享响应字节和异步加载是源码可见的实现差异，但本轮没有消融实验，不能量化每项改动的独立贡献。
