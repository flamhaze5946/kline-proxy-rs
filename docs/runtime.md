# 0.4.22 运行、恢复与持久化

这一阶段补齐 K 线数据的运行生命周期。核心提交规则与 bulk 等待继续由 `kline-core`、`kline-service` 管理；网络历史加载、落盘和健康协调放入独立的 `kline-runtime`，避免把后台 I/O 引入请求路径。

## 启动与就绪

1. 读取配置，建立静态目录并按 subscriptions 发现动态目录，校验每条序列的容量、时间间隔与边界保护窗口。
2. 校验并恢复本地快照，再加载可选种子文件。
3. 启动 HTTP、WebSocket、时钟同步、REST 恢复与定期持久化任务。
4. 已启用 REST 时，所有正在交易的序列都必须完成当前连接周期的数据恢复，保留历史连续、尾部新鲜；每条连接须实际收到匹配目录的 K 线，时钟也须满足配置要求，才返回就绪。

`/health/live` 是进程存活检查。`/health/ready` 返回 200 或 503，以及序列恢复数量、后台任务数、连接数、收到数据的连接数和时钟偏移。`strict_readiness=true`（Rust 默认值）时未就绪的 bulk 返回 503；Java 转换配置设为 false，允许继续查询保留数据，两种策略均保留真实健康状态。显式不配置 `rest` 的离线/开发模式保留“所有序列已有数据”的旧就绪条件。

0.4.12 的 `unready_reasons` 显示 initial_pending、epoch_pending、gap_pending、stale_tail。原因可重叠，不应相加作为未就绪总数。尾部新鲜度考察最新已观测记录；低成交量标的在收到最终收盘帧后尚无下一根形成中记录，也可能在宽限后触发 stale_tail。因此全局 readiness 与某批最新已收盘 bulk 的完整性应分别观察。

0.4.15 允许已收到紧邻上一根 `x=true` 的序列在查询时构造临时零成交量 bar；它可满足尾部可查询条件，真实新鲜度单独统计。最终帧迟到、尾部过期和静默重订阅不再触发即时 REST，只等待定时订正；启动加载和实际重连恢复暂保留。完整门槛、`provisional_current` / `observed_stale_tail` 及部署状态见 [当前周期占位说明](current-zero-bar-20260928.md)。

WebSocket 断开或检测到新历史缺口会立即使就绪失效；协调器每 250ms 检查状态，但缺口提示不会提前定时订正。实际连接重连仍安排恢复。仅重新建立 TCP/WebSocket 连接不代表恢复完成。时间同步超过 10 分钟未成功或连接超过 180 秒无 I/O，也不能报告就绪。新鲜度检查给最终帧保留默认 15 秒宽限；正常整点的 bulk 仍按自身等待预算处理最终确认。

动态目录在元数据有效期的 80% 处刷新，默认 300 秒有效期对应约 240 秒。上新、下架、状态及容量变化按稳定 ID 更新；K 线每条连接最多 200 个主题（`websocket.batch_size`，可调小）；显式配置的 stream URL 在启动时校验，不超过 Binance 单连接 1024 个流。同一进程的全部 WebSocket 建连尝试（K 线与 ticker 的首次连接、重连和 23 小时轮换）按到达顺序排队：相邻两次尝试至少间隔 100ms，任意 5 分钟内最多 150 次；放行前（排队中）被取消的不计数，放行后一律计数，即使随后没有真正建连；进程停顿后醒来的尝试也照样间隔发出，下一次尝试要等上一次的调用方真正恢复后才开始计间隔。150 是 Binance 每 IP 每 5 分钟 300 次的一半，这个上限写在现货文档里，合约按同样处理。节流只约束发起尝试的时刻，不包含 DNS、TLS 握手、收到首帧和恢复的时间。配置了持久化目录时，尝试时间也写入其中的 `ws-connect-attempts.json`（同步落盘后改名替换），重启后的进程接着同一个 5 分钟窗口计数，崩溃循环共用一份额度。这有几个前提：同一时间只有一个服务实例写这个文件；从记录到下次启动读取之间墙钟没有向前跳（向前跳会让记录提前过期）；记录的时间可能比实际建连早一次写盘的时长，通常只有几毫秒；只防进程崩溃和重启；文件读写失败或未配置持久化时只覆盖当前进程，并记录警告。一次建连放行后，记录会在下一次建连之前写完。同一 IP 上的其他程序不计入。systemd 的重启间隔为 30 秒。显式 URL 的流数量同时计入 `streams=` 查询参数和 `/ws/` 路径里列出的流。每条连接的重订阅请求会合并，每秒最多发一对 UNSUBSCRIBE/SUBSCRIBE，等待间隔期间照常读帧，给 PONG 留出余量（Binance 每连接每秒最多收 5 条（现货）或 10 条（合约）消息，PONG 也计入）。某主题超过默认 120 秒没有消息时，只重新订阅该主题，保留正常连接和其他序列的恢复进度；重订阅及其 recheck 提示不新增即时 REST 请求。例行校验本身不会撤销已有有效数据的就绪状态；实际断线、历史缺口和尾部过期仍影响就绪判断。显式配置的流必须自行覆盖需要的数据；逐主题重订阅仅用于自动生成的订阅，显式连接仍受连接空闲超时和周期 REST 校验保护。

0.4.22 将元数据、已编码响应和币种索引作为同一份不可变快照发布。刷新不清空旧快照，读请求在原有效期内直接使用它；exchangeInfo 和普通元数据校验仍为一个有效期，ticker 币种查询保留两个有效期的原有宽限。已过硬期限的快照不会伪装成新数据；真正冷启动最多等待 5 秒。独立维护任务也刷新已使用但没有 K 线订阅的市场。`/health/market.metadata` 可检查快照年龄、刷新状态、加载次数和失败次数。

## REST 恢复

冷启动从最新数据向前分页，最多加载配置的保留容量。恢复阶段从最新最终记录或更早的非最终记录/缺口开始，并重读最近 `future_refresh_count` / `spot_refresh_count` 根（默认 99；null 为保留容量），向当前时间补齐；长期离线只处理保留窗口。向前分页同时限制 `startTime` 与 `endTime`，避免接口按最新 LIMIT 条取数时漏掉窗口前部。

合约默认每页 499 条，现货最多 1000 条。合约分页采用较低的请求权重档；权重按实际 limit 计算。规则来源：[Binance 合约市场数据](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/market-data)、[现货市场数据](https://developers.binance.com/en/docs/catalog/core-trading-spot-trading/api/rest-api/market)。

REST 返回数据经过长度、数值、顺序、时间范围和重复检查，通过统一提交规则与 WebSocket 合并。相同交易笔数的 REST 记录不能覆盖已有流版本；新的流式最终帧仍按原有优先级修正形成中数据。REST 历史补齐会使对应市场的已缓存 bulk 响应失效。

最终状态以本次恢复请求开始前捕获的时间为准：请求在收盘前发起、响应在收盘后到达，不能据此把当时尚未收盘的数据标成最终。已有更晚的实时消息也不能掩盖中间未补齐的历史缺口。

固定间隔内的内部缺口保留 Java 的零成交量补齐方式，只在实际观测之间补齐，不向最后一根真实记录之后虚构数据。月线按真实开收盘时间判断连续性，跨月缺口需要真实 REST 记录，不能按固定 30 天造月线。bulk 的 `1w`/`1M` 等待边界仍保留 Java 的固定时长算法，日历边界一致性尚需独立处理。

REST 客户端复用连接；连接超时 5 秒、请求超时 15 秒、Kline 响应上限 2MiB（目录 32MiB，ticker 8MiB）。每市场共享平滑权重预算，429/418 的 `Retry-After` 会推迟该市场的所有等待请求；网络错误与 5xx 最多尝试 3 次。冷却规则依据 [Binance 现货 REST 说明](https://developers.binance.com/en/docs/products/spot/rest-api)。预算只协调当前 Rust 进程，其他进程仍会占用同一出口的交易所配额。

## 边界保护与调度

0.4.22 在市场共享权重预算内分别保留 Urgent、Metadata、PriceRefresh 的额度。默认 1200/min 对应 20、60、120；普通后台最多使用 1000。启动与重连恢复也属于 Urgent，但用尽短突发额度后不再持续抢占元数据和价格刷新。价格、元数据及普通前台可借用有上限的平滑发送额度，硬分钟预算和 429/418 冷却始终有效，因此一秒调度目标不是所有网络和负载条件下的响应保证。资金通道不预留自身不用的市场额度。

| 配置 | 默认值 | 行为 |
|---|---:|---|
| `rest.weight_per_minute` | 1200 | 每市场请求权重预算 |
| `rest.workers` | 4 | 同时恢复的序列数 |
| `rest.reconcile_seconds` | 300 | 一条序列恢复成功后的复查间隔 |
| `rest.future_refresh_count` / `spot_refresh_count` | 99 | 定期重新核对已有历史；null 使用容量 |
| `rest.hour_boundary_guard_before_ms` / `after_ms` | 0 / 0 | 额外整点保护；Java 转换值 150000 / 30000 |
| `rest.retry_seconds` | 10 | 恢复失败后重试间隔 |
| `rest.boundary_guard_before_ms` | 3000 | 边界前暂缓非冷启动 REST 页请求 |
| `rest.boundary_guard_after_ms` | 10000 | 边界后暂缓非冷启动 REST 页请求 |
| `rest.freshness_grace_ms` | 15000 | 数据尾部宽限 |
| `rest.sync_clock` | true | 每 60 秒采样交易所时间 |
| `persistence.interval_seconds` | 300 | 干净完成后等待下一次落盘 |
| `persistence.boundary_guard_before_ms` | 30000 | 边界前暂缓开始下一条序列写盘 |
| `persistence.boundary_guard_after_ms` | 30000 | 边界后暂缓开始下一条序列写盘 |

边界保护按所有配置间隔生效；两侧保护之和必须小于最短间隔。例如使用 1m 时，持久化不能沿用前后各 30 秒的默认值，应缩短保护窗口。已经发出的请求或开始的文件写入不会强制中断。冷启动跳过 REST 保护，最终退出落盘跳过磁盘保护，避免无法启动或保存。

协调器轮询分配恢复任务，避免目录前部长期占满恢复并发。后台任务不持有序列锁等待网络或磁盘；恢复批量提交每 256 条主动让出执行权。持久化由单个写入者在阻塞工作线程执行。它们仍共享进程 CPU，边界保护并不等于操作系统层面的资源隔离。

时钟每轮取 3 次采样中 RTT 最小的有效结果，要求 RTT 不超过 1000ms，偏移绝对值小于 5 分钟。`clock_offset_ms` 是初始偏移；自动同步开启后会更新它。未开启自动同步时由配置提供偏移。

## 快照与退出

快照按市场、间隔、symbol 生成独立文件名。文件带版本、序列身份、时间、记录数与 SHA-256 校验；double 快照继续使用 v1 和原始 f64 位模式；其他模式使用 v2，保留模式标记、float 精确值、string 原文或 BigDecimal 的系数与 scale。两版均可读取，变更配置模式时，先完整转换并校验再发布，转换失败不会加载半个文件。只保存已最终确认且时间已收盘的记录，不保存形成中 K 线。

写入流程为同目录临时文件 → 文件 fsync → 原子 rename → 目录 fsync。只确认成功写入时捕获的 dirty generation，并发提交仍保持待写状态。延期或失败也保持待写：边界延期约 1 秒后检查，写入失败约 10 秒后重试。全部记录都不可持久化时，不用空快照覆盖已有历史。

恢复前先校验完整文件，再发布任何记录；损坏、身份不匹配、乱序或包含未来数据的快照被跳过，由 REST 重新加载。`.kpr` 格式与 Java JSON 不同；配置 legacy_directory 可只读导入 version=1 的日分片。导入不修改 Java 文件，先验证文件格式与身份，损坏日跳过；日内无法解析的单条数据按 Java 行为跳过，其他有效记录保留；成功后生成校验过的 Rust 快照。同一持久化目录应由一个进程独占。

SIGINT/SIGTERM 先停止上游和恢复写入，给 HTTP 请求最多 35 秒排空，再完成最后一次快照并退出。最终落盘仍受磁盘自身完成时间约束。

## 资金费率与辅助任务

`market_api` 默认启用。资金费率在启动时预热，随后睡眠到每小时发布宽限后与 :05 重试；默认宽限 50ms。小时缓存 720 项，全市场近期结果 64 项/60 秒。指定币种的近期查询按 `(symbol, limit, hour, revision)` 缓存，最多 2048 项、60 秒；不同客户端组合共享同一币种加载，不再叠加第二层响应体有效期。原始代理及范围查询保持原语义。资金请求使用独立的 100 次/分钟平滑限速通道，429/418 冷却会作用于相应通道。它不代替出口级限额协调。

`market_api.funding.vision_enabled` 控制公开月 ZIP 预载，默认近 30 天、16 个下载任务。404 表示该标的缺归档，按 Java 行为跳过；其他下载错误或 ZIP/header 解析失败使该月不发布。CSV 内非法行单独跳过，支持字段周边空格和额外列。解压与编码不占用 I/O 或 bulk 编码线程。`funding.enabled` 和 `statistics.enabled` 控制后台作业，HTTP 路由仍可按需查询；`market_api.enabled=false` 则关闭整组辅助路由和后台任务。

合约 ticker 使用 !ticker@arr；现货根据当前交易目录使用逐标的 @ticker，每连接最多 200 个主题，每 60 秒协调一次。启用行情流的市场每 60 秒刷新 24hr REST 基线；未启用行情流时，收到全市场查询后启动短期按需刷新。单 symbol 优先读取有效 WS 观测：24h ticker 和现货价格来自 ticker，合约价格按需求订阅 aggTrade 并保留实际成交时间。连接断开、观测超过 3 秒或合约观测落后于已见 REST 时间时回退 REST；等待期间新的有效 WS 值也能释放请求。行情查询总预算 5 秒，包含额度等待。

全市场价格由独立 REST 基线和 WS 发布任务维护：有访问时以 500ms 为基线刷新目标，约每 100ms 合入有效 WS 行，编码快照最多复用 250ms，REST 基线硬期限为 10 秒；重新编码不会延长该期限。没有 WS 覆盖的行使用期限内的 REST 值，超过期限需刷新；这些策略并非 Java 的旧快照无限回退语义。全市场 24h ticker 的响应字节缓存仍为 500ms。AltCoin/Yama 数据与 PNG 缓存 60 秒，CMS 缓存 5 分钟。ATR 启动后每小时记录，历史不足时跳过。

## 诊断口径

closed_only bulk 请求若在周期边界（如整点）之前 `bulk_pre_boundary_wait_ms`（默认 250 ms，0 关闭，上限 1 s）以内到达，先等到边界再处理，与 Java 1.8.10 的 `kline.bulk.preBoundaryWaitMs` 一致：这类请求来自时钟略快于本机的调用方，要的是边界处刚收盘的 bar；否则会按上一个周期返回旧数据。等待之后，这个请求的时间不早于边界（时钟仍差一点时也一样），并继续等待刚收盘 bar 的 final。更早到达的请求不等；每次等待记一条 `BULK_PRE_BOUNDARY_WAIT` 日志，`/metrics` 增加 `kline_bulk_pre_boundary_waits_total`。每个 closed_only 请求一旦选定边界就只进不退：排队等名额或重试时即使时钟被同步往回调，也不会退回上一个周期。等待 final 的截止时间按单调时钟定下：请求第一次选定某个边界时算好（从边界起算的 `final_wait_ms`），排队等名额和重试时沿用；由它创建的在途 key 存下这个截止时间，之后加入或接手构建的请求沿用在途 key 的，不会因时钟回调重新计时。`/health/performance` 的整点统计按 bulk 请求实际应答的周期归类：在边界之前到达、等到边界（或排队跨过边界）才应答的请求计入新的小时，并从边界起算判断是否属于整点首 10 秒；其他请求按到达时间归类，耗时一律按实际计算。

bulk 判定周期边界（选边界、边界前等待、构建响应和校验缓存是否仍有效）用的时间，取本机时钟与服务器时间估计（`sync_clock` 同步得到的 offset）两者中较晚的一个，由 `bulk_host_clock_floor` 控制（默认开启；`false` 时只用服务器时间估计，即旧行为）。这样估计落后于真实时钟时，整点后刚到的请求不会被当成边界之前、按上一个周期返回不含刚收盘 bar 的结果；等待 final 的截止时间同样从这个时间所在的边界起算。只有 bulk 使用它，其余逻辑（REST 订正、边界保护、健康检查、统计）仍只用服务器时间估计。

bulk 同一时刻最多保留 `bulk_inflight_limit`（默认 256）个不同的在途 key，在途指正在等待收盘确认或正在构建。新 key 遇到名额已满时，不再立即返回 503，而是进入先进先出队列等待名额。排队上限为 `bulk_admission_queue`（默认 4096），单个请求最长等待 `bulk_admission_wait_ms`（未配置时等于 `final_wait_ms`），超出任一上限才返回 503 -1008 `Response capacity exceeded`。命中缓存、或加入已有在途 key 的请求不占名额。整点时每个 closed_only key 都会占住名额直到收盘确认，这些名额通常在一两百毫秒内释放；2026-09-30 的同机测试中，392 个不同 key 同时到达，在旧的固定上限下每小时有 136 个被直接拒绝。`/metrics` 增加 `kline_bulk_admission_queued_total`、`kline_bulk_admission_rejected_total` 和 `kline_bulk_admission_waiting`。

HTTP 请求在进入路由前还要取得所在路由组的名额（K 线 bulk 等核心路由一组，资金费率、行情等市场接口一组），每组默认最多同时处理 `http_concurrency_limit`（512）个请求。满了以后同样排队等待：每组最多 `http_admission_queue`（默认 4096）个，最长等待 `http_admission_wait_ms`（未配置时等于 `final_wait_ms`），超出才返回 503 -1008 `Request capacity exceeded`。整点时正在等待收盘确认的 bulk 请求会一直占着路由组名额，旧版本超过 512 个就直接拒绝。`/health*`、`/actuator*`、`/metrics` 不经过名额与排队，满载时探活和指标采集照常响应。等待名额的截止时间是严格的：名额若在截止之后才轮到，会还给下一个排队者并返回 503。排队时间从请求到达路由组时开始计，HTTP 排队也不会超过所在路由自己的预算，超出同样返回 503 -1008 `Request capacity exceeded`：bulk 等待在途名额的时间与 HTTP 排队共用同一个 `bulk_admission_wait_ms` 预算，HTTP 排队最多等到这个预算用完；行情查询（`ticker/price`、`ticker/24hr`）的 5 秒总预算同样从请求到达时开始计，HTTP 排队最多 5 秒；交易所元数据首次加载的 5 秒预算同样从请求到达时开始计，但 HTTP 排队不按它截断，因为一个请求是否需要元数据取决于它的参数和请求体。首次加载只发生在该市场的元数据第一次加载成功之前（没人用到的市场可能很久之后才加载）；这期间如果市场组排队超过 5 秒，而请求拿到名额时仍需要首次加载，它会因预算已用完立即返回 503。配置在引擎中钳位：并发与在途名额 1–65536，排队长度不超过 1048576，等待不超过 30000 ms。`/metrics` 增加 `kline_http_admission_queued_total`、`kline_http_admission_rejected_total` 和 `kline_http_admission_waiting`（两组合计）。

大 JSON 解码、元数据整形、归档解析和大资金响应最多占用一个 market CPU worker，并在占用共享队列容量之前取得大任务许可。Yama 三种结果共用一次 60 秒缓存计算，由独立的单 worker 统计池计算和绘图。bulk 大请求额外限制为最多 8 个已入队任务，避免占满 64 个通用槽位而阻塞近期小查询；取消请求不会提前释放仍在执行任务的资源许可。release 保留原生符号供 `perf` 排查，调试段不映射进进程 RSS。

`/health/diagnostics` 保存每个市场/周期最近 24 个收盘摘要；`/health/performance` 还包含最近 24 小时的 HTTP bulk 数据。收盘字段包括预期/已到/缺失、first/p50/p99/max、最慢 symbol、最后接收、事件到接收、解析与提交耗时。8 秒未齐标记 timed_out，不把部分集合当全部就绪。`closed_bar_latency_enabled=false` 关闭逐帧解析/提交细分计时，仍保留收盘到达摘要；输出显式标记 `detailed_latency_enabled=false`。

HTTP p99 从进入应用到生成响应统计，不包含 Nginx/TLS、客户端网络或发送完全部字节。boundary_* 只统计每小时前 10 秒发起且成功的 bulk；整小时统计另外包含错误数量。每市场每小时最多保存 65536 个耗时样本，超额明确列出 dropped_samples。数据内存保存，重启清空；生产长期留存应采集 Prometheus 和日志。

`/health/market` 提供两个市场的 ticker 帧数/缓存标的数及资金加载/小时缓存数。`/actuator/health` 返回 UP/DOWN，`/actuator/info` 返回版本，`/actuator/prometheus` 和 `/metrics` 提供相同 Rust 指标。
