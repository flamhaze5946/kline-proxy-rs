**0.4.13 部署后首个整点实测：closed K 线数据一致，本轮 Rust bulk 更快；全局就绪状态仍有短暂波动。**

观测整点为 **2026-09-28 16:00 UTC / 20:00 迪拜**。Rust 使用 192.0.2.40 上的 0.4.13，Java 为 market.feng.dog 的现有实例 192.0.2.30；东京测试机为 192.0.2.10。本轮未修改或重启生产服务。发布身份与配置见[部署记录](parity-deployment-20260928.md)。

两边各 200 个客户端，同一组分散的 5 个 symbol，POST `/fapi/v1/klines/bulk`，`interval=1h&limit=10&closed_only=true`。727 个共同具备完整历史窗口的合约币种全部被覆盖。最新期望收盘柱的 openTime 为 15:00 UTC（1790607600000）。计划在整点后 10 ms 发起，实测发起范围为整点后 **29.29～35.36 ms**。这次没有覆盖整点之前或最初 29 ms 的竞态。

“入缓存”不代表磁盘持久化。Java 使用 `CLOSED_BAR_LATENCY.ready_offset_ms_max`，Rust 使用开启详细记录后的 `closed_bars.max_ms`；两者均按各服务的交易所校准时钟计时。客户端耗时从发起请求到完整读取响应结束，包括等待收盘和 Nginx/网络，但不包括之后的 JSON 校验。跨服务的几毫秒差异受时钟校准与不同 WebSocket 链路影响，不能据此推导精确的逐段差值。p99 使用 200 个请求的 nearest-rank 第 198 个值，最大值单列，未剔除慢请求。

**数据核对**

- 200 对请求的 K 线业务内容逐字段相等，独立的规范化 SHA-256 也为 **200/200 相等**。
- 400 个响应都包含对应的 5 个 symbol × 10 根 K 线，最后一根为本次最新收盘柱，`finalized=true`、`pending=[]`。Rust 的 `data_status` 也全部报告完整、无缺失、无未终态币种。
- 整点后约 5 秒再次查询，与各自整点响应比较，**400/400 没有后续改值**。
- 后续全市场查询的 **732 个合约窗口全部相等**，没有单边多出或缺少的币种。5 个历史不足 10 根的新币种未加入突发负载池，但包含在这次全市场复核中。
- BTC/ETH/SOL/BNB/XRP 的现货单币接口，固定同一截止时间后最近 10 根收盘柱 **5/5 组、50 根相等**。这是突发请求结束后的现货值核对，未对现货做相同的 200 并发对比；Java 没有对应的现货 bulk 路由。

全部 400 条客户端 TLS 连接在整点之前建立并成功复用，排除了测试机集中 TLS 握手的开销；本轮不包含 Lambda 容器冷启动、冷 TLS 或其实际出口链路。客户端计时窗口内共享 CPU 用量为 0.061 秒、总墙钟时间 1.048 秒，请求发起分散约 6.05 ms。预热的 `/fapi/v1/time` 请求发生在前一分钟，没有混入整点计时结果。

Java 最慢请求标识 `kp0413-h16-java-future-reuse-00-022`，客户端耗时 1042.242 ms；对应 Nginx 日志 `rt=1.040 uct=1.039 uht=1.041 urt=1.041`，响应内 `waited_ms=0`。因此这笔请求的主要延迟在 Nginx 建立到应用的连接阶段，没有花一秒等待收盘数据。同期监听队列溢出、Java backlog 为 100，而 Rust 为 1024，支持监听队列拥塞这一解释；没有逐连接抓包，不能把所有 TCP 重传都归到这笔请求。此处各计时字段有约 1 ms 的量化差异，不做严格减法。

**仍需跟进的就绪状态**

| 整点后采样时间 | Rust `/health/ready` | stale_tail 序列数 |
|---|---:|---:|
| +5、+15 秒 | 200 | 0 |
| +30 秒 | 503 | 25 |
| +60 秒 | 503 | 10 |
| +120 秒 | 503 | 2 |
| +180 秒 | 503 | 1 |
| +240 秒 | 200 | 0 |

这是离散采样，不能把 +30 或 +240 秒当成精确故障开始/恢复时间。各采样点的小时收盘统计始终为两市场全部到齐、pending 为空，`latest_repair_jobs=0`，WebSocket 14/14；没有发现最新 closed bar 缺失。Java 的 `/actuator/health` 在所有采样点为 200，但其检查语义与 Rust 的 `/health/ready` 不同，不能直接当作相同检查的优劣对比。

源码中 `lifecycle_status` 分别计算 `fresh_tail` 与 `needs_final`；前者检查缓存尾部 K 线时间是否仍在容许范围，后者检查目标收盘柱是否终态。已经拥有上一小时完整收盘柱，不必然代表新一小时的活动柱已经到达。因此不能把 `stale_tail` 等同于已收盘数据丢失。此次健康快照没有受影响 symbol 明细，未证明每条 stale 序列的具体上游原因。生产配置保持 `strict_readiness=false`，该全局状态不会直接拒绝 bulk；本次计时业务请求发生在状态变差之前，不能用这些请求声称已验证整个 503 窗口中的业务可用性。

另外，原始日志在 16:00:00.025 出现一次资金费率整点快照为空、保留至 `:05` 重试的告警。代码中的 `:05` 是整点后 **5 分钟**，不是 5 秒。本轮没有采集整点资金费率接口的配对响应，不能从本次 K 线通过推断资金费率整点行为也已完全对齐，也不能仅凭该告警认定已经发生数据错误。
