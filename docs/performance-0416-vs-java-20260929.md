**Java 1.8.3 与 Rust 0.4.16 实例性能对比 · 2026-09-29**

状态：全部三个计划整点均已完成。

当前部署下，Rust 在近期 K 线 bulk 并发查询中有明显响应优势，优势不限于内存。CPU 优势取决于负载，部分单币查询的 p99 仍高于 Java；Rust 还出现过一次全市场价格 503。因此本轮支持“核心 bulk 场景更快”，不支持“所有性能和可用性都优于 Java”。

测试端为东京 VPS；目标为实际运行的 market.feng.dog 与 market-mirror.feng.dog。以下时间均为 UTC。两端保持部署版本和配置，保留正常后台任务及生产流量。

**200 个客户端，每个请求 5 个分散币种、每个币种最近 10 根已收盘 1h K 线**

先完成了非整点 10 轮配对测试，每端 2,000 次请求。主测试复用预先建立的 TLS/HTTP1.1 连接；请求计时包含读取完整响应，不含 JSON 校验。

| 指标 | Java | Rust |
|---|---:|---:|
| bulk p50 | 57.71 ms | 15.03 ms |
| bulk p99 | 117.26 ms | 30.32 ms |
| bulk 最大耗时 | 124.14 ms | 32.37 ms |
| 每轮 200 个请求全部完成，中位时间 | 106.42 ms | 26.99 ms |
| 每轮全部完成，最慢一轮 | 128.42 ms | 36.42 ms |
| 请求错误 | 0 / 2,000 | 0 / 2,000 |

该场景 Rust 的 p99 降低 74.1%。2,000 组配对响应中的 K 线内容全部相同，所有请求均复用连接。Java、Rust 的 Nginx upstream response time p99 分别为 109 ms、27 ms，差距主要出现在服务端。

逐轮复核，10 轮的每轮 p99 都是 Rust 更低：Java 各轮为 91.3～122.9 ms，Rust 为 18.9～32.2 ms。该优势并非单个 Java 慢请求拉高汇总值。

**整点实测**

|---|---:|---:|---:|---:|
| 06:00，回查 | 124.33 / 117.08 ms | 149.24 / 133.01 ms | 未施加测试负载 | 未施加测试负载 |
| 07:00 | 173.25 / 166.02 ms | 115.31 / 114.05 ms | 429.62 / 161.77 ms | 457.37 / 180.47 ms |

各整点的数据校验及可用性：

- 07:00：配对 K 线一致 200/200；Rust 就绪检查异常 0/452；采样最大 stale_tail=0。
- 08:00：配对 K 线一致 200/200；Rust 就绪检查异常 0/452；采样最大 stale_tail=0。
- 09:00：配对 K 线一致 200/200；Rust 就绪检查异常 245/452；采样最大 stale_tail=2。

09:00 必须单独说明：整点后 +32.5 秒新增 CRMLUSDT，配置序列由 2,456 增为 2,458。其 1h、1d 序列初始化期间，全局 readiness 在 245/452 次采样中返回 503；+190.1 秒恢复，总计观察到约 157.6 秒的异常窗口。

stale_tail=2 仅出现在 +32.5、+33.0 秒两次采样；+33.5 秒起 stale_tail 已为 0，但 initial_pending=2、epoch_pending=2 一直阻止全局就绪，直到初始化完成。异常窗口内 ready_series 保持 2,456，原有币种的业务抽查均正常。新增币种初始化与全局 readiness 的联动仍需要处理，不能宣称“整点后再也不会返回 503”。

代码确认，新序列与定时订正共用恢复调度，并且必须完成初始化、确认订阅 epoch 才计入就绪。本次没有逐任务排队与执行时间埋点，不能把约 157.6 秒全部归因于 REST 限流。Java actuator health 与该数据就绪检查语义不同，未把二者直接作为可用率对比。

全部合约 closed bar 就绪后，到本轮最后一个 bulk 响应读完的时间差：

| UTC 整点 | Java | Rust |
|---|---:|---:|
| 07:00 | 284.12 ms | 14.44 ms |
| 08:00 | 256.60 ms | 16.61 ms |

此差值用于观察数据收齐后的交付滞后，混合了请求调度、处理、传输及跨机时钟误差，不是单次查询的纯 CPU 耗时。本轮 200 个请求覆盖全部 732 个共同合约币种。

- 08:00 首秒完成记录的额外生产请求：Java 391，Rust 0。按 Nginx 日志完成时间分桶，不含每端额外施加的 200 个测试请求。
- 09:00 首秒完成记录的额外生产请求：Java 391，Rust 0。按 Nginx 日志完成时间分桶，不含每端额外施加的 200 个测试请求。

**相同混合负载，非整点对照**

200 个客户端各并行请求同一组 5 个币种的 K 线和资金费率，双方每轮各 400 次请求，共 10 轮。资金费率使用固定近期窗口、每币种 1 条；K 线为最近 10 根已收盘 1h。预热与 JSON 校验均在计时之外。

| 指标 | Java | Rust |
|---|---:|---:|
| K 线 bulk p50 / p99 | 91.73 / 1027.06 ms | 38.41 / 66.24 ms |
| 资金费率 bulk p50 / p99 | 68.17 / 1039.00 ms | 37.31 / 65.78 ms |
| 每轮 200 客户端两接口全部完成，中位时间 | 171.19 ms | 62.94 ms |
| 同期应用 CPU 均值 | 18.30% | 11.95% |

两端各 4,000 次请求均成功，2,000 组 K 线与 2,000 组资金费率内容全部一致。共同币种池为 732 个。Rust funding upstream_loads 在本次固定窗口测试前后保持 13，没有额外 REST 加载。

Java 有 122 次 Nginx 上游连接等待超过 900 ms，ListenOverflows、ListenDrops、TCPSynRetrans 同期均增加 122；Rust 四项均为 0。现有应用监听队列分别为 100 和 1024。因而 Java 约 1 秒的 p99 含有明显的连接队列瓶颈，不能称为 Rust 语言快了十几倍。

仅为诊断而剔除上游连接 ≥900 ms 的样本后，Java K 线 bulk 剩余 1952 次，p99 为 186.48 ms；Rust 全部 2,000 次的 p99 为 66.24 ms。该条件筛选不等于改完队列之后的真实性能预测，正式结果仍保留全部请求。

这组测试让额外施加的 API 数量、参数、币种和连接方式一致；没有复现生产 POST 正文及精确到达时序。观测窗口 Java 仍另有约 435 个生产请求，Rust 无对应流量。TLS 预热请求已单独分类，未混入生产流量。

**已定位的长尾**

- Java：06:06:44 的 G1 GC 暂停 462.798 ms，safepoint 总计 463.688 ms；同轮 10 个请求耗时 422.6～454.9 ms。Nginx upstream 时间与请求重叠的 GC 日志一致。
- Rust：06:07:25 发起的现货全市场价格请求耗时 5,003.4 ms 后返回 503。对应价格后台刷新在本机限流器等待 15,852.1 ms，而实际 REST HTTP 耗时 22.7 ms、状态 200、cooldown_rounds=0。此前的价格基线超过 10 秒有效期，请求等待刷新后撞上 5 秒超时。单独的锁等待时间未埋点；等待链由部署代码与这些时间点共同支持。
- 测试期间没有重启、调参或部署修复。该 Rust 价格问题仍需要处理，不能用 bulk 的速度优势掩盖可用性问题。

**口径与证据**

- 两端 Nginx 均为 1.26.3，worker_connections=768，上游 keepalive=64、keepalive_timeout=15s、keepalive_requests=90，均使用上游 HTTP/1.1 并清空 Connection 头。应用监听队列仍分别为 Java 100、Rust 1024。
- 复用 TLS 的主结果没有包含 Lambda 冷启动与冷 TLS 握手。客户端 Go 驱动在东京运行，端点通过正确域名的 TLS 校验直接连接各实例 IP。
- 行情随时间变化，价格接口仅检查有效响应；确定已经收盘的 K 线才逐值比较。Java 没有对应的现货 bulk 接口，现货对比使用双方共有的单币接口。
- 整点收盘验证针对 1h 周期；1d 的平时查询已测试，但本轮没有覆盖 UTC 00:00 的日线换日。
- Java 与 Rust 的 closed bar 计时使用各自的交易所校正时钟。几毫秒的跨机差异应谨慎解读；客户端延迟由同一测试机计时。
- CPU 平均值按采样时长加权；07:00 为约 1 秒采样，后续整点在前 1 秒至后 2 秒以 100 ms 采样并对齐整点。不同分辨率的峰值不能直接比较，具体采样时窗保留在 JSON。
